关键问题标注

🔴 P0: 系统通知路径与引擎消息注入的时序竞态

现象：系统通知（如子任务完成）先推送 WS 事件创建前端气泡，然后才调用 engine.inject_message()。如果引擎在 running 状态且下一轮迭代未开始，前端看到通知但 AI 不知道。

根本原因：非 user 来源的消息分两阶段处理：先推送 system_notification（约第270行），再调用 inject_message（约第373行）。两者无同步保障。

🔴 P0: system_notification 降级路径过多

非 user 来源有 4 条降级路径：① bridge 缓冲 → ② event_sink 推送 → ③ send_frontend_event fallback → ④ 放弃。每条路径的 level 计算和 notificationType 拼接略有不一致。

🟡 P1: pipeline_received 事件前端被忽略

后端在 source='user' 时发送 pipeline_received，但前端 handlePipelineReceived 看见 source='user' 直接 return。这个事件在所有用户场景都是空操作。

🟡 P1: inject_message 的 running 与 suspended 路径行为不对称

9. 简化与改进方案

9.1 架构简化

✅ 方案1：合并系统通知的两条路径 (P0-1)

当前：系统消息 → ① 推送 WS + ② inject_message（两条路径无同步）

改进：先注入引擎 → 引擎确认后 → 再推送前端

# 新流程
async def send_pipeline_message(...):
    engine.inject_message(message, source=source)  # 1. 先注入
    engine_seq = await engine.confirm_queued()      # 2. 等待确认
    if source != "user":
        await _send_system_notification(pipeline_id, message, engine_seq)  # 3. 再前端

✅ 方案2：消除 pipeline_received 空操作 (P1-6)

删除 _send_received_event 和 handlePipelineReceived。

✅ 方案3：stream_end/new_message 改为可靠两阶段确认 (P0-3)

改进：stream_end 携带 message_persisted:true。后端先持久化再发 stream_end。前端收到 stream_end 直接标记 completed，不再依赖 new_message。

# 后端 drain_loop 退出
await bridge.send_new_message(content)  # 先持久化
await bridge._send_event(stream_end)    # 再发终止 → 前端直接 completed

9.2 代码简化

✅ 方案4：系统通知降级路径合并 (P0-5)

# 简化为单一出口
if source != "user":
    await send_frontend_event(pipeline_id, {
        "type": "system_notification",
        "data": {"content": message, "pipeline_id": pipeline_id, ...}
    })

流式缓冲逻辑移到 send_frontend_event 内部统一处理。

✅ 方案5：_pending_notifications 结构化 (P1-1/P1-2)

@dataclass
class Notification:
    content: str; source: str; timestamp: float
    priority: int; notification_id: str  # 去重 key

9.3 其他改进

✅ 方案6：重连补漏改为后端主动推送 (P0-4)

后端 WS Server 重连时主动检查 pipeline 状态并发送 missed_messages 事件。前端不再自己推理 state。

✅ 方案7：统一 Markdown 渲染器 (P2-1)

只保留 LobeChatMarkdown，评估 Streamdown 是否可替代。

✅ 方案8：chunk 超时改为后端感知 (P1-7)

前端不设盲定时器，依赖后端 stream_keepalive。N 秒无保活才判定超时。

10.2 核心错误链 — LLM API 调用持续失败

现象：从 20:09:22 到 20:16:35，Minimax API 持续返回 tool call id is invalid (2013) 错误，每条间隔约 5-10 秒，共产生约 24 次重试，全部失败。

10.5 日志缺失与诊断盲区

🟡 P1: 关键诊断日志虽已实施但实际未触发

通过 grep 搜索所有 logs/pipeline/*.log 发现：

  1. 无 CancelledError 日志：搜索不到 CancelledError 或 RAW_ERROR — 说明管道中断路径绕过了 engine.py 的异常捕获
  2. 无引擎退出摘要：搜索不到 _run_loop finally — 说明引擎的 finally 块可能未执行
  3. 无 task_post_pipeline 诊断：搜索不到 _fail_after_pipeline_exit — 说明任务失败判断走了不同的代码路径
  4. 5 个 error 日志为空：这些管道的 WARNING/ERROR 没有被分类写入

结论：之前补充的 5 处日志点在本次执行中全部未触发，说明管道中断的实际路径可能不同于预期（可能是在 LLM 重试耗尽后直接失败，而非被 CancelledError 中断）。
