# 代码实现

> **本技能是流程指引，不是逐条打勾清单**：按场景判断使用，遇不适用情况保持裁量，不机械执行。
> 流程骨架的顺序真值常驻于消费方提示词（code_writer 等编码执行者）；本文件是骨架各步的细节展开，按需读取对应节，不另立骨架顺序。

## 执行流程

### 第 1 步：确认需要（编码前必做）

进入编码前，先确认输入和目标就绪，缺则停下追问，不靠猜测推进。

1. **确认功能目标**：逐条过验收标准（AC），确认每条都理解且可执行；有 state_machine 时确认要覆盖所有状态和转换
2. **确认涉及范围**：本任务要改哪些模块/文件，各自职责是什么
3. **确认技术栈与约束**：前端/后端/全栈；前端任务的设计系统约束；接口契约变更预期
4. **上下文获取按需自定**：读什么、读多少由你按任务性质决定——新代码任务的 API 契约由测试定义（见第 4 步）；存量代码改动按定位需要读取
5. **信息不全的处理**：影响验收判据理解的关键缺口通过 human_interaction 向上追问；仅影响实现细节的不必等待——按最合理形态实现并在注释标注"假设"

### 第 2 步：调研现有实现（防重复实现、防破坏架构）

读多少由任务性质决定：

- **新代码任务**（新建模块/插件/文件为主体）：契约由你的测试定义，可直接进入测试设计
- **存量改动任务**（修改既有模块/跨模块交互）：核对上下游接口与可复用项，到"能安全落笔"为止
- 深度自定：单文件小改通常无需深挖；拿不准是否复用时倾向读一眼接口签名而非整链路

### 第 3 步：模块边界设计

按 coding_domain_rules.md §5.2 执行模块边界设计。

新增文件前先更新所在模块的「结构 > 文件清单」，改接口前先更新模块级/项目级文档（文档不存在先创建）。

**迁移/重构任务（强制门禁）**：涉及迁移旧代码、大规模重构、修改多个模块交互方式时，必须先执行架构审查：
1. 使用 file_read 读取涉及的旧代码/现有架构，梳理模块结构、依赖关系、数据流向，产出架构摘要
2. 标注现有架构中的耦合点和内聚性问题
3. 将架构审查报告写入 `docs/working/architecture_review_report.md`，必须包含：(1) 现有架构概述 (2) 计划变更范围 (3) 接口契约变更清单 (4) 风险评估
4. 调用 task_evaluate 标记架构审查完成，**通过 human_interaction 向用户确认后再编码**；禁止未经确认就开始修改架构

新建任务跳过此步。

### 第 4 步：测试设计（Red 阶段，先写失败测试）

**这一步就是设计动作**：新代码的 API 契约由你的测试定义——函数名/签名/返回结构按你的设计写，不确定的外部依赖用最小桩；修改存量代码时，以既有测试与接口签名为准。

**测试分工裁定**（任务书携带签发验收测试时）：

| 测试类别 | 产出方 | 编码方权限 |
|---|---|---|
| 辅助单测 | 编码方随实现同步编写 | 可写可改——断言与覆盖随设计迭代调整 |
| 签发验收测试 | 独立起草方起草、签发方签发冻结 | 只读执行——原样运行，不改断言、不跳过用例 |

签发验收测试是验收证据的来源，编码方改动它等于自产验收证据。发现签发验收测试与实现冲突时，回退给起草方与签发方重签，不在本次实现中改测试。起草方按 `skills/skill-acceptance-test-authoring/SKILL.md` 的可渲染约定书写，编码方按本裁定执行。

已有测试可复用时自行判断（已覆盖场景跳过、只补缺失）。

场景覆盖清单（补缺失部分）：
- **正常场景**：标准输入，预期成功
- **边界场景**：最小/最大值、空值、临界值
- **异常场景**：错误输入、异常处理路径
- **状态机**：有 state_machine 时，覆盖所有状态和转换（state_coverage=100%，transition_coverage=100%）

测试类型选择：
- 单元测试：单函数/方法，隔离外部依赖
- 集成测试：多组件协作，验证模块间交互
- **API 端点测试**（后端/全栈任务必做）：每端点覆盖 2xx 成功 + 4xx 客户端错误 + 5xx 服务端错误，校验响应 Schema
- **前端 E2E**（前端任务必做）：用 bash_execute 跑 `npx playwright test` 做浏览器级测试，不能只用 Jest 组件测试代替

**防拟合要求**（测试怎么写，实现才无法靠硬编码期望值/路径刷绿）：按 coding_domain_rules §6.5 执行——同一行为 ≥2 组有区分度输入、关键行为配性质断言、可枚举输入 parametrize、关键路径走真实依赖断言，禁止单点输入拟合/全 mock。

写完测试**必须运行确认全部失败（Red）**，保留失败证据。禁止在本阶段写实现代码。
**接口契约测试**：跨模块交互必须编写接口契约测试，验证调用方与被调用方的接口约定。

### 第 5 步：实现代码（Green 阶段）

1. 写最少的代码让测试通过
2. 每个公共接口的实际实现必须与第 3 步的契约一致
3. 完整类型注解和文档字符串
4. 每个 must 级 AC 必须在代码中有对应实现
5. **复用落地**：第 2 步判定为"直接复用/需修改现有实现"的，按结论执行；禁止在实现阶段另起炉灶重复造轮子
6. 运行测试确认通过（Green）
7. **防拟合自检**：实现必须满足契约而非具体测试用例——(a) 泛化性自检：用测试集之外的同契约输入验证结果正确；(b) 删值实验：把疑似硬编码的返回值/路径改为其他值，相关测试必须变红。禁止以硬编码测试期望值作为实现终态（TDD 过渡硬编码必须由后续用例驱动移除）

### 第 6 步：重构优化（Refactor 阶段）

测试全通过后才能重构：
- 消除重复代码、改善命名和可读性
- **内聚性检查**：每个模块/文件职责单一，不相关功能已拆分
- **耦合度检查**：模块间只通过公共接口交互，无隐式耦合
- 每次重构后运行测试确保仍通过

### 第 7 步：回归验证

1. 运行全部测试套件（不只是新写的）
2. 检查覆盖率：核心逻辑 100% 分支覆盖，一般代码 80%（按 testing_rules 的 P0/P1/P2 分级）
3. **接口一致性验证**：所有公共接口实现与契约文档一致
4. 确认无残留临时诊断代码（print/console.log 等）
5. **修复沉淀**：若本次含缺陷修复，须落沉淀——项目有测试基建则回归测试入测试车道；项目有 agentos CI（`.agentos/ci/`）则可落 `local/` 门禁（模式扫描/文件断言 checker），二选一留痕（AGENTS.md「新代码带测试」的项目侧承载）

## 编码完成后的风险分级

在编排执行报告中标注本次改动命中的风险维度（用于追溯改动范围）：
- **接口契约变更**：新增/修改/删除对外接口、函数签名、数据结构、配置项
- **跨模块改动**：涉及 ≥2 个模块（非同模块多文件）
- **安全相关**：认证、鉴权、加密、密钥、权限、用户数据
- **数据持久化**：数据库 schema、配置文件结构、状态存储
- **控制流核心**：主循环、状态机、任务调度、错误处理策略

## 规则

- TDD 红绿循环不可跳过：必须先写测试并确认 Red，再写实现使其 Green
- 提交 task_evaluate 前必须运行全部测试并通过
- 每个 must 级 AC 必须在代码中实现
- 前端代码必须遵守设计系统约束（间距、颜色、组件使用规范）
- 门禁回退修复时用 `file_write` 的 search_replace 动作定向修改，禁止重写整个文件
- 修改代码局限在最小范围，优先改现有文件，除非必要不新建文件
- 新增文件前必须先更新模块「结构 > 文件清单」，文档不存在先创建
- 修改接口/配置前必须先更新对应模块级和项目级文档
- 禁止重复实现：能直接调用或修改现有实现满足需求时，禁止新建；新建必须有"为何不适用现有实现"的理由
- 编码前必须先摸清现有相关实现并核对接口契约和架构边界，没看到就动手视为不合格
- 签发验收测试（任务书携带时）只读执行：改断言、跳用例一律不做——冲突回退起草方与签发方重签
- 如果输入包含 state_machine，测试必须覆盖所有状态和转换
- API 端点测试必须覆盖 2xx 和 4xx 场景，必须做 Schema 校验
- 必须先搜现有测试文件，有现成测试时优先复用和补充，禁止另起炉灶
- 测试禁止单点输入拟合：同一行为 ≥2 组有区分度输入，关键行为配性质断言（见 coding_domain_rules §6.5）
- 实现禁止为刷绿硬编码期望值/路径：必须通过泛化性自检（测试集外输入仍正确），否则按「测试拟合实现」反模式打回
