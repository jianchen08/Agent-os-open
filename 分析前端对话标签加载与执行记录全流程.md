## 二、对话标签 (Tab) 加载流程 —— 全分支

### 2.1 标签体系架构

前端支持三层标签页：

```
L1 (主Agent 标签)          L2 (子Agent 标签)          L3 (孙Agent 标签)
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│ 灵汐 (主对话)    │      │ 代码审查员       │      │ 子任务执行器     │
│ agentLevel=1    │      │ agentLevel=2    │      │ agentLevel=3    │
│ pipelineRunId=A │      │ pipelineRunId=B │      │ pipelineRunId=C │
│ parentRecordId  │      │ parentRecordId  │      │ parentRecordId  │
│   = null        │      │   = A           │      │   = B           │
└─────────────────┘      └─────────────────┘      └─────────────────┘
```

**状态管理**: `agentTabStore` 维护 `tabs[]`、`pipelineTabMap`（pipelineId → tabId）、`activeTabId`。

### 2.2 Tab 创建的所有分支

```
分支 1: 创建新会话
  sessionListStore.createSession()
    → 后端 POST /api/v1/threads (X-Main-Agent-Request: true)
    → 后端返回 {session_id, active_pipeline_id, pipeline_ids}
    → pipelineStore.registerPipeline({pipelineId, level:1})
    → pipelineStore.activatePipeline(pipelineId)

分支 2: WebSocket 子Agent创建 (运行时)
  WS 事件: sub_agent_created
    → handleSubAgentCreated()
    → agentTabStore.openSubAgentTab({pipelineId, taskId, agentName})
    → pipelineStore.registerPipeline({pipelineId, level:2/3})
    → agentTabStore.registerPipelineTab(pipelineId, tabId)

分支 3: 页面刷新 / 重新进入会话
  ChatContainer useEffect (sessionId 变化)
    → agentTabStore.initSessionTabs(sessionId)
      → 从 localStorage(`agent-tabs-{sessionId}`) 恢复 Tab 状态
      → 如果存在子 Tab 的 pipelineId
        → pipelineStore.registerPipeline() 注册但暂不加载消息
        → 仅在切换到该 Tab 时才加载消息

分支 4: 会话切换 (点击会话列表)
  sessionListStore.setActiveSession(sessionId)
    → uiStorage.setLastActiveSession(id)  // 持久化到 localStorage
    → pipelineStore.fetchMessages(pipelineId, {threadId})  // 加载历史消息
    → ChatContainer useEffect 触发 Tab 恢复
```

### 2.3 Tab 切换流程

```
用户点击 Tab
  → agentTabStore.switchToTab(tabId)
  → 设置 activeTabId
  → pipelineStore.activatePipeline(tab.pipelineRunId)  // 重置未读计数

  → ChatContainer 选择器响应:
    effectiveId = activeTab.pipelineRunId || pipelineStore.activePipelineId
    pipelineMessages = s.messagesByPipeline[effectiveId]

  → 如果 Tab 对应管道尚未加载消息:
    → agentTabStore.loadTabMessages(tabId)
    → pipelineStore.fetchMessages(pipelineRunId, {threadId: sessionId})
```

### 2.4 Tab 关闭流程

```
agentTabStore.closeTab(tabId)
  → 从 tabs[] 中移除
  → 从 pipelineTabMap 中移除映射
  → 如果被关闭的是当前激活 Tab:
    → 切换到主 Tab (agentLevel=1)
    → pipelineStore.activatePipeline(主管道ID)
  → 注意: 不删除 pipelineMessageStore 中的消息数据 (保留缓存)
```

### 2.5 SubTabRouter 路由守卫

`SubTabRouter` 是无 UI 逻辑组件，确保消息正确路由：

```
职责 1: pipeline→Tab 映射注册
  遍历 tabs，对 agentLevel≠1 的 Tab，自动注册 pipelineTabMap

职责 2: 消息路由 (routeMessageToTab)
  优先级: Tab存在 → 直接写入; Tab不存在 → 缓冲30秒; 超时 → fallback到主Tab

职责 3: 输入路由验证 (validateInputRouting)
  验证子Tab输入的 parentRecordId 与 Tab 的 parentRecordId 是否匹配

职责 4: 发布到 window.__subTabRouter 供外部使用
```

## 三、后端执行记录加载流程

### 3.1 执行记录的存储模型

```
data/pipelines/
  {pipeline_run_id}.yaml          ← 单管道 ≤500条记录
  {pipeline_run_id}_002.yaml      ← 超过500条时分片 (自动递增编号)
  {root_task_id}/                 ← 子任务管道按根任务分组
    {pipeline_run_id}.yaml
  _pipeline_root_map.json          ← 管道ID→根任务ID映射
```

**YAML 文件结构**:
```yaml
summary:
  run_id: "xxx"
  thread_id: "yyy"
  total_iterations: 5
  total_tokens: {prompt: 1000, completion: 500}
  status: "completed"
records:
- record_id: "rec-001"
  pipeline_run_id: "xxx"
  type: ai           # ai | tool | user | system
  content: "..."
  sequence: 1
  iteration: 1
  tool_calls_json: [...]
  thinking_content: "..."
```

### 3.2 后端 API 路由 (核心)

| 端点 | 功能 | 核心函数 |
|------|------|----------|
| `GET /api/v1/threads/{thread_id}/messages` | **获取消息列表** | `list_messages()` → `exec_storage.list_by_pipeline()` |
| `GET /api/v1/threads/{thread_id}/detail` | **获取线程详情+执行图** | `get_thread_detail()` → `_build_execution_graph()` |
| `GET /api/v1/threads/{thread_id}/state` | 获取线程状态 | 返回 SessionModel 状态 |
| `GET /api/v1/threads/{thread_id}/history` | 获取历史 | 游标分页 |

### 3.3 消息列表查询 (`list_messages`) 完整链路

```
前端请求:
  GET /api/v1/threads/{thread_id}/messages
    ?pipeline_run_id=xxx
    &limit=50
    &before_sequence=100   // 向上翻页
    &after_sequence=200    // 断线补漏

后端处理:
  1. _get_execution_record_storage() → 获取 ExecutionRecordStorage 单例
  2. target_pid = pipeline_run_id || thread_id
  3. exec_storage.list_by_pipeline(target_pid, limit, before_sequence, after_sequence)
     ├── limit != null → read_records_from_tail() [尾部反向读优化]
     │   ├── 读取YAML文件末尾64KB窗口
     │   ├── 按 "\n- " 切分record块
     │   ├── 跨分片累积到 limit 条
     │   └── safe_load 反序列化 → 按sequence排序
     │
     └── limit == null → _list_by_pipeline_full() [全量加载]
         └── 完整 YAML safe_load → 过滤 → 排序

  4. _record_to_message_response(r, thread_id) 对每条记录做转换:
     ExecutionRecordData → MessageResponse {id, role, content, parts[], ...}
     - type=user → role=user
     - type=ai → role=assistant (含thinkingContent, toolCalls→parts)
     - type=tool → role=tool (含toolName, toolArgs, toolResult)
     - [系统提示]前缀 → role=system

  5. 返回 {messages, total, has_more}
```

### 3.4 尾部反向读优化（关键性能优化）

```
问题: 主管道单文件 1.3MB / 500条record，全量 YAML safe_load 要 4-5s
方案: 只读文件末尾 64KB 窗口
效果: 降至 0.3-0.8s

实现:
  1. open(file, 'r') → seek(-64KB, SEEK_END)
  2. 在窗口内找到 \n-  作为 record 块边界
  3. 不足 limit 条时跨分片累积 (打开 _002.yaml 等)
  4. 拼装最小 YAML 文档 → safe_load
  5. 按 sequence 排序 + 截断到 limit
```

### 3.5 执行记录创建链路（由 PipelineEngine 驱动）

```
用户输入 → WebSocket → app_factory.py
  → send_pipeline_message()
    ├── 分支A: 引擎 Running → engine.inject_message()
    ├── 分支B: 引擎 Suspended → engine.inject_message() 唤醒
    ├── 分支C: 无引擎有历史 → _try_revive_pipeline() 重建引擎
    └── 分支D: 无引擎无历史 → 返回失败

PipelineEngine.run()
  → 输入插件链 → LLM调用 → 输出插件链
    → TrackPlugin (输出插件)
      → execution_record_storage.save(record)
        → YAML 文件增量追加 (append模式)
        → 超过500条触发分片

引擎完成:
  → execution_record_storage.save_summary(summary)
  → update_summary(pid, {thread_id: "xxx"})
```

## 四、前端消息数据流的三个入口路径

所有消息最终都写入 `pipelineMessageStore`，通过 `pipelineId` 索引。

### 路径 A: 冷启动 (REST API 加载历史)

```
触发时机:
  - 创建新会话 (无消息)
  - 切换到已有会话
  - 页面刷新后进入

链路:
  sessionListStore.setActiveSession(sessionId)
    → pipelineStore.fetchMessages(pipelineId, {threadId})
      → 并发去重检查 (_fetchingPipelines Map)
      → retry(3次, 429重试) → apiGetMessages(threadId, {pipelineRunId, limit:50})
        → 后端 GET /api/v1/threads/{threadId}/messages
          → list_messages → list_by_pipeline → read_records_from_tail
          → _record_to_message_response × N
      → 前端收到: {messages: Message[], total, has_more}
      → session.ts: mergeConsecutiveAssistantMessages(messages) [详见§4.1]
      → pipelineStore.initFromAPI(pipelineId, messages, hasMoreOlder)
        → mergeApiWithExisting: 保留本地 streaming 消息，其余以 API 为准
        → 设置双游标: topCursor=最小sequence, bottomCursor=最大sequence
        → 设置 hasMoreOlderByPipeline

  ChatContainer useEffect (sessionId变化)
    → agentTabStore.initSessionTabs(sessionId)
    → pipelineStore.activatePipeline(pipelineId) // 仅激活，不再重复fetch

渲染:
  ChatContainer 选择器:
    effectiveId = activeTab.pipelineRunId || pipelineStore.activePipelineId
    pipelineMessages = s.messagesByPipeline[effectiveId]
  → activeMessages = pipelineMessages.filter(role !== 'tool')
  → 搜索过滤 → MessageList (Virtuoso 虚拟滚动)
```

### 路径 B: 流式更新 (WebSocket 实时推送)

```
触发时机:
  - 用户发送消息后，后端 PipelineEngine 开始输出
  - 任何时刻（前台/后台标签均可接收）

完整生命周期:

┌─ stream_start ─────────────────────────────────────┐
│ resolvePipelineId(eventData) → pipelineId           │
│ 管道未注册 → auto-register                          │
│ ensureStreamingPlaceholder(pipelineId, messageId)   │
│   ├── startPipelineStreaming() [双Store同步]        │
│   ├── 清理旧 streaming 占位符                       │
│   └── addMessage(pipelineId, {role:assistant,       │
│         status:'streaming', parts:[]})              │
│ 如果 activePipelineId ≠ pipelineId:                 │
│   如果 activeTab.pipelineRunId == pipelineId:       │
│     → activatePipeline(pipelineId)                 │
└────────────────────────────────────────────────────┘

┌─ stream_chunk (可能有 N 个) ────────────────────────┐
│ resolvePipelineId → pipelineId                      │
│ 消息未找到 → ensureStreamingPlaceholder (兜底)       │
│ 缓冲: _chunkBuffer.set(`${pid}::${mid}`, chunks)    │
│ _scheduleFlush() → requestAnimationFrame 批处理      │
│   → 同一帧内多个chunk合并为一次 store更新            │
│   → findStreamingPartIndex → appendToPart()          │
│ timeout: 120s 无chunk则触发chunk超时                 │
│   → handleChunkTimeout: 有内容→保留completed         │
│                        无内容→标记error+通知          │
└────────────────────────────────────────────────────┘

┌─ thinking_start / thinking_chunk / thinking_end ────┐
│ handleThinkingStart:                                │
│   → appendPart(pipelineId, messageId, {type:thinking,│
│       content:'', state:'streaming'})               │
│   → 30s 后备超时计时器                              │
│ handleThinkingChunk:                                │
│   → findLastPartIndex → appendToPart (增量追加)      │
│   → 重置超时计时器                                  │
│ handleThinkingEnd:                                  │
│   → updatePart(state:'done') + 计算耗时              │
└────────────────────────────────────────────────────┘

┌─ tool_start / tool_result ──────────────────────────┐
│ handleToolStart:                                    │
│   → callId 去重检查                                 │
│   → appendPart({type:'tool_call', state:'calling'}) │
│ handleToolResult:                                   │
│   → findToolCallPartIndex(callId) 精确定位          │
│   → updatePart({state:'done', result, durationMs})  │
│   → 回填 "unknown" 工具名                           │
└────────────────────────────────────────────────────┘

┌─ stream_end ────────────────────────────────────────┐
│ flushStreamChunkBuffer() [先刷写残留chunk]           │
│ terminatePipeline() [清理超时+双Store流式状态]        │
│ 如果后端返回了完整 parts[]:                          │
│   → updateMessage(pipelineId, messageId,             │
│       {parts: serverParts, status:'completed'})     │
│   后端未发 parts → fallback:                         │
│   → finalizeMessage() [所有part.state→done]          │
│ 更新 usage (token统计)                              │
└────────────────────────────────────────────────────┘

┌─ stream_error ──────────────────────────────────────┐
│ flushStreamChunkBuffer()                            │
│ terminatePipeline()                                 │
│ updateMessage({status:'error'})                     │
│ streaming parts → done, tool_call parts → error     │
│ 发送通知: "流式响应错误"                              │
└────────────────────────────────────────────────────┘

┌─ new_message (后端权威数据同步) ────────────────────┐
│ 后端在 drain_loop 结束时发送，携带完整 parts[]       │
│ 作为权威版本完整替换流式增量构建的消息                │
│ → updateMessage({parts: serverParts, status:xxx})   │
└────────────────────────────────────────────────────┘
```

### 路径 C: 断线补漏 (重连后 fetch)

```
触发: WebSocket 重连 (handleReconnected)

步骤:
  1. 清理残留 streaming thinking parts → state='done'
  2. 清理 streamingStore 中不再活跃的 tab
  3. 对每个 streamingState[pipelineId].isStreaming == true 的管道:
     pipelineStore.fetchMessages(pipelineId, {
       after_sequence: bottomCursor,
       threadId: sessionId,
     })
     → appendMessages(pipelineId, messages)  [追加到底部+去重]
     
  4. 特殊场景: 页面刷新后 WS 重连
     后端继续发送 stream_start → 前端创建占位消息
     用户点击会话 → 本地消息 <=1 条 → 强制 fetchMessages
     否则 → 跳过 fetchMessages (保留流式数据不被 API 覆盖)
```

## 五、渲染流程 (Message → Part → Fragment → DOM)

### 5.1 渲染管线总览

```
pipelineMessageStore.messagesByPipeline[pipelineId]
  │
  ▼
ChatContainer 选择器
  │ pipelineMessages = s.messagesByPipeline[effectiveId]
  │ activeMessages = pipelineMessages.filter(role !== 'tool')
  │ filteredMessages = 搜索过滤
  │
  ▼
MessageList (Virtuoso 虚拟滚动)
  │ itemContent(index, message) → MessageItem
  │
  ▼
MessageItem
  │ 根据 message.role 选择容器样式:
  │  user → 右对齐气泡
  │  assistant → AI气泡 (pending时显示思考动画)
  │  tool → 独立工具消息
  │  system → 系统通知样式
  │
  │ 核心调用: useMessageRender(message)
  │
  ▼
useMessageRender (核心渲染 Hook)
  │ 从 message.parts[] 构建 RenderFragment[]


  │ Part 类型 → Fragment 类型映射:
  │
  │ thinking part ──────→ ThinkingDisplay 组件
  │   ├── 步骤列表 (reasoning/analysis/planning/evaluation)
  │   ├── 流式Markdown/纯文本
  │   └── state=streaming → 旋转loading动画
  │
  │ text part ──────────→ LobeChatMarkdown / MarkdownRenderer
  │   最后一个text part 且 state=streaming → 打字机效果
  │   其他 → 正常Markdown渲染
  │
  │ tool_call part ─────→ ActivityCard 组件
  │   ├── state=calling → 呼吸动画
  │   ├── state=done → 状态图标+耗时
  │   ├── state=error → 红色错误标识
  │   ├── 展开详情: 参数/结果/错误/操作按钮
  │   └── enhanceActivityWithToolConfig (UI配置增强)
  │
  │ system part ────────→ 系统通知样式div
  │   └── level (info/warning/error) → 颜色+图标
  │
  │
  ▼
MessageContentRenderer (统一渲染入口)
  │ React.memo 优化
  │ 按 RenderFragment.type 分发:
  │  thinking → ThinkingDisplay
  │  text → MarkdownRenderer
  │  tool_call → ActivityCard
  │  system → 系统通知div
  │
  ▼
DOM (最终输出)
```

### 5.2 稳定 Key 策略（防止流式闪烁）

```
useMessageRender 使用 makeStablePartKey(part, partIndex):

  tool_call → `tool-${part.callId}`          (不变)
  thinking → `thinking-${partIndex}`          (唯一)
  text     → `text-${partIndex}`
  system   → `sys-${partIndex}`

  不使用 part.content 作为 key → 流式追加content时 React 不会重建DOM
  只通过 content 变化触发文本更新，不触发组件卸载/挂载
```

### 5.3 消息合并 (mergeConsecutiveAssistantMessages)

**问题背景**: 后端将同一次 LLM 响应的 text 和 tool_calls 拆成多条 ExecutionRecordData:

```
后端YAML:
  record-1: type=ai, role=assistant, content="", tool_calls=[{call_id:tc1, name:search}]
  record-2: type=tool, role=tool, toolCallId=tc1, result={...}
  record-3: type=tool, role=tool, toolCallId=tc2, result={...}
  record-4: type=ai, role=assistant, content="根据查询结果..."
```

**合并策略** (只用于 API 历史加载，流式路径不受影响):

```
第一遍: 吸收 tool 消息
  for assistant 消息:
    收集它后面的所有 tool 消息
    将 tool 的 result/error 注入到相应 tool_call part
  
第二遍: 合并连续 assistant
  for 连续的 assistant 消息:
    合并 content (换行拼接)
    合并 parts (重编号 sequence)
    输出为一条消息
```

### 5.4 特殊渲染行为

| 场景 | 行为 |
|------|------|
| 流式输出中 | 最后一个 text part 显示打字机效果 (state=streaming) |
| tool_call 调用中 | ActivityCard 显示呼吸动画 (state=calling) |
| 思考过程 | 默认折叠，可展开 (state=streaming时显示loading) |
| 系统通知 | 不参与合并，直接渲染为独立样式气泡 |
| 空 assistant 占位符 | ensureStreamingPlaceholder 会清理旧占位符 |
| 消息搜索 | 过滤 content 和 tool_call.name |

## 六、流式配合机制

### 6.1 双通道架构

```
              ┌─── 实时通道: WebSocket ───┐
              │   stream_start → stream_   │
用户发送消息   │   chunk(×N) → stream_end │  前端渲染
              │   事件驱动、增量更新       │
              └───────────────────────────┘

              ┌─── 历史通道: REST API ────┐
会话切换/刷新  │   GET /threads/{id}/       │  前端加载
              │   messages → Message[]    │
              │   拉取模式、批量写入       │
              └───────────────────────────┘
```

### 6.2 流式与 API 数据的合并策略

```
场景 1: 正常冷启动 (无本地消息)
  fetchMessages → API返回100条 → initFromAPI → 直接写入

场景 2: 冷启动时管道正在流式输出
  stream_start先到 → 创建占位消息 (status=streaming)
  fetchMessages → API返回99条 (不含streaming消息，后端还未持久化最新一条)
  initFromAPI → mergeApiWithExisting:
    apiIds = Set(API消息ID)
    streamingOnly = existing.filter(status==='streaming' && !apiIds.has(id))
    finalMessages = mergeSorted(apiSorted, streamingOnly)
  结果: 99条历史 + 1条流式 → 100条，流式继续更新

场景 3: 断线重连
  handleReconnected → fetchMessages(after_sequence=bottomCursor)
  → appendMessages → 去重追加

场景 4: 页面刷新后回到正在输出的会话
  WS重连 → stream_start → 占位消息
  用户点击 → existingCount==1 → 强制fetchMessages (不跳过)
  initFromAPI → streaming消息保留

场景 5: 切换回正在输出的会话 (非刷新)
  isStreaming=true && existingCount>1 → 跳过fetchMessages
  (保留流式数据不被API覆盖)
```

### 6.3 RAF 批处理 (性能关键)

```
问题: 大模型输出快时，一帧内可能收到 10+ 个 stream_chunk
      每次 chunk 都更新 Zustand store → 触发 10+ 次 React 重渲染 → UI 卡顿

方案:
  _chunkBuffer Map: `${pipelineId}::${messageId}` → {chunks[]}
  _scheduleFlush(): 使用 requestAnimationFrame
    同一帧内多次 chunk 只调度一次 RAF 回调
  RAF 回调中将 chunks join 后一次性 appendToPart

效果: N次store更新压缩为1次
```

### 6.4 超时与保活机制

```
chunk 超时 (120秒):
  - 每次收到非终止流式事件 → resetChunkTimeout
  - 终止事件 (stream_end/error/new_message) → 清理
  - 超时回调:
    消息有内容 → status='completed' 保留
    消息无内容 → status='error' + 通知用户

keepalive (stream_keepalive事件):
  - 后端定期发送 (LLM思考期间)
  - 前端仅重置超时，不做数据操作

thinking 独立超时 (30秒):
  - thinking_start 时启动
  - thinking_chunk 时重置
  - thinking_end 时清理
```

### 6.5 WebSocket 生命周期

```
连接建立:
  GlobalWebSocket 单例 (路径: /ws/chat)
  → 心跳检测 (30s间隔, 30s超时)
  → 版本协商 (PROTOCOL_VERSION: "3.0.0")
  → 注册会话 → connection_confirmation

连接断开/重连:
  → 指数退避重连 (4s起始, 60s上限, 30次)
  → 发送队列管理 (重连后重放)
  → handleReconnected() 清理 + 补漏

消息发送:
  sendUserInput(data) → WS发送json
  sendCancel(threadId, reason) → 取消信号
  sendApproval(requestId, approved) → 人类交互批准
```
