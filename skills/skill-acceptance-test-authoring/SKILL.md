# 验收测试起草（Acceptance Test Authoring）

> **本技能是流程指引，不是逐条打勾清单**：按场景判断使用，遇不适用情况保持裁量，不机械执行。
> **本件给独立起草方用**：起草方与实现方**异构**（不同基座模型 / 不同会话上下文 / 不共享提示历史），且**看不到**本轮实现与实现方自述——避免反向适配。签发权与 diff 确认权留人类。

## 〇、定位与边界

| 项 | 内容 |
|---|---|
| 谁写 | 独立起草方（AI 或人类），与实现方异构 |
| 写什么 | 签发级验收测试：行为断言 + 边界 + 异常 + 并发/时序（需求涉及才要）+ 契约测试 |
| 不写什么 | 不写实现；不写"辅助单测"（那是实现方自产，不作验收证据）；不改需求措辞 |
| 交给谁 | 审查方复检 → 人类签发冻结 → 编码方**只读执行** |
| 配套件 | `skills/skill-requirement-battle/SKILL.md`（需求冻结侧产物：AC 清单 / 状态机 / 边界场景 / 签发记录 / 预绑定范围表） |

**起草方的输入只有三样**：冻结的需求（AC + 状态机 + 边界场景）、前置契约、上一版测试代码。**禁止**看实现代码与实现方自述理由。

## 一、可渲染约定（书写规范，不是另一层文档）

人类读的是从测试代码**自动渲染**出的规格页（意图 / 关键示例 / 边界覆盖 / 失败报告），不是手写规格文档——手写页会漂移。因此测试代码本身必须满足可渲染约定。

### 1.1 命名约定

测试名必须包含**需求ID + 场景描述**：

```
test_REQ_042_注册3天首单满100_优惠20
```

- 需求ID 原样出现在测试名里（`REQ-042` / `AC-007` 依冻结版本口径），使状态矩阵能从测试结果自动推导。
- 场景描述写**场景本身**（"注册3天首单满100"），不写"正常情况"这类无信息词。
- 同一需求下的多条测试用场景描述区分，不靠编号后缀凑数。

### 1.2 结构约定：四段式

测试代码按 **输入数据 / 执行 / 输出断言 / 副作用断言** 四段组织，**数据段用结构化对象**而非散落在断言里：

```python
def test_REQ_042_注册3天首单满100_优惠20():
    # --- 输入数据 ---
    ctx = build_context(register_days_ago=3, order_amount=100)

    # --- 执行 ---
    result = apply_discount(ctx)

    # --- 输出断言 ---
    assert result.discount == 20
    assert result.final_amount == 80

    # --- 副作用断言 ---
    assert db_snapshot_of_orders() == expected_order_record(discount=20)
```

- 输入数据段**必须**是结构化对象（fixture / builder / 参数字典），散落在各条断言里的字面量不可渲染、不可复用。
- 副作用段缺失时**显式写"无副作用"并说明理由**（不留空白让人猜是不是漏写）。

### 1.3 场景分组

同一需求下的测试按 **正常路径 / 边界 / 异常 / 并发** 分组，渲染页按组折叠。用 pytest 时用 `class` 分组或 marker 分组，命名保持可渲染：

```python
class TestREQ042正常路径: ...
class TestREQ042边界: ...
class TestREQ042异常: ...
class TestREQ042并发: ...
```

### 1.4 失败报告约定（人类化，不出裸堆栈）

断言失败时输出：**场景名 / 输入 / 期望 / 实际 / 相关需求ID / 失败断言位置**。禁止只抛裸堆栈或裸 pytest 默认消息。

```python
def test_REQ_042_注册3天首单满100_优惠20():
    ctx = build_context(register_days_ago=3, order_amount=100)
    result = apply_discount(ctx)
    assert result.discount == 20, describe(
        scenario="注册3天首单满100_优惠20",
        requirement_id="REQ-042",
        input={"register_days_ago": 3, "order_amount": 100},
        expected={"discount": 20},
        actual={"discount": result.discount},
        location="apply_discount.discount",
    )
```

- `describe(...)` 输出人类可读的一行摘要，**不吞异常**、不替代断言本身。
- 失败定位信息要指到**断言位置**（函数/字段/行），不能只说"断言失败"。

### 1.5 副作用显式声明

副作用断言必须写明**观测接口**（outbox / 外部调用桩记录 / 状态快照 / 日志拦截），渲染页据此展示副作用矩阵。没写观测接口的副作用不允许进契约。

### 1.6 禁止不可渲染结构

| 禁止 | 原因 |
|---|---|
| 动态拼接断言目标（`assert getattr(obj, field) == v`，field 运行时算） | 渲染页看不出断言的是什么 |
| 断言目标来自运行时不可预测数据（时间戳、随机 ID 未固定） | 无法复现、无法渲染期望值 |
| 关键断言藏在辅助函数深处而测试名不反映 | 人类读规格页时看不到关键判据 |
| 关键断言塞进 `if` 条件分支 | 条件不成立时测试静默通过 |

## 二、签名测试审查清单（审查对象是测试代码，不是实现）

清单由**起草方自检 → 审查方复检 → 人类签发确认**三道走。任一条不通过即打回。

### 2.1 平凡实现可骗过性

断言必须能挡住"什么都没做对"的实现。以下四类断言**一律不合格**：

| 不合格断言 | 为什么骗得过 |
|---|---|
| 只断言返回值非空 | `return {}` 也能过 |
| 只断言不抛异常 | 空实现也能过 |
| 只断言日志包含关键词 | 打印关键词即可骗过 |
| 只断言状态码 2xx | 什么都不做也返回 2xx |

合格做法：断言到**契约粒度**——具体字段值、具体错误类型、具体副作用内容与次数。

### 2.2 边界覆盖

按需求涉及的维度覆盖：**下界 / 上界 / 空 / 超长 / 并发**（时序按需求是否涉及）。缺哪一维由需求的边界场景清单决定（冻结需求里有哪维就必须有哪维的用例）。

### 2.3 异常路径断言错误类型与语义

不只断言"抛了异常"，要断言**错误类型 + 错误语义**（错误码/错误消息关键片段/错误对象上的字段）。`except Exception: pass` 式断言等于没断言。

### 2.4 冗余度

同一需求的多条测试若**删掉一半仍全绿**，说明断言重复、覆盖不均——要么补上缺失的行为断言，要么合并。冗余度与变异测试配合判断：删除关键业务判断后总闸仍全绿 = 测试本身失效，必须回溯需求层重签。

### 2.5 断言与需求语义对应

断言要对应**需求语义**，而不是只耦合实现细节。判据：换一种合规实现（内部结构不同、外部行为相同）时断言应仍成立；反之，只在某个具体内部结构下才成立的断言是过拟合。

### 2.6 测试内绕过

审查测试**自身**：测试里是否吞异常、跳过断言、条件断言（`if` 包住 assert）、用 `try/except` 把失败吃掉。测试内绕过一律不合格。

### 2.7 副作用覆盖

断言是否覆盖契约声明的**全部**副作用：写库内容与次数、消息 payload、外部调用参数、状态变更、缓存变更、事件发出、权限/状态变更。漏一个就是覆盖缺口。

## 三、副作用断言写法（复用仓内既有设施，不自造）

观测基础设施已现成，用 `skills/skill-test-infra/SKILL.md` 的三脚本：

| 要断言的副作用 | 用哪个脚本 | 典型用法 |
|---|---|---|
| 消息/通知/外部调用 | `side_effect_mock.py` | `serve` 启动 mock 记录全部副作用 → `verify` 按预期 JSON 校验 payload 与次数 |
| 数据库写入内容 | `db_snapshot.py` | 操作前 `create` 快照 → 操作后 `diff` 对比（可断言写入内容与次数） |
| 日志/事件触发 | `log_interceptor.py` | 按规则 JSON 拦截提取，断言关键事件是否触发、参数是否正确 |

```bash
# 外部通知副作用：起 mock 记录 → 操作 → 按预期校验
python skills/skill-test-infra/scripts/side_effect_mock.py serve --port <端口> --output <记录路径>
python skills/skill-test-infra/scripts/side_effect_mock.py verify --record <记录路径> --expect <预期JSON>

# 数据库写入：操作前快照 → 操作后对比
python skills/skill-test-infra/scripts/db_snapshot.py create --tables <表名,逗号分隔> --output <快照路径>
python skills/skill-test-infra/scripts/db_snapshot.py diff --before <前> --after <后>

# 日志/事件：按规则拦截提取
python skills/skill-test-infra/scripts/log_interceptor.py --log-file <日志路径> --rules <规则JSON>
```

要点：

- **可观测性不足先改架构，不改测试**：不可观测的副作用 = 不可验证的需求。要求副作用可断言的接口（outbox / 桩记录 / 快照）必须在设计时就留出接缝；接缝缺失是**需求/架构缺口**，回报提出方，不是在测试里绕过去。
- 脚本细节与参数以 `skills/skill-test-infra/SKILL.md` 为准（**引用不复述**，防双真值漂移）。

## 四、输入随机化 / 模糊化约定

**目的**：防止实现方针对固定 fixture 做"应试优化"（实现只在被断言的那几个输入上正确）。

- **固定 fixture 之外**，按需求属性生成随机边界输入与模糊输入。
- **按需求属性生成**，不是无脑 fuzz：生成维度来自该需求的边界场景清单（数值上界、字符串长度、集合规模、时间偏移、并发度等）。
- **必须可复现**：随机用固定种子（`random.Random(seed)`），失败报告里带**实际输入**（不是带种子让人重跑）——复现靠记录输入，不靠复现环境。
- **性质断言优先**：随机输入的断言写**性质/关系**（单调性、范围、不变量、幂等性），不是逐个期望值。
- **数量下限**：每条 must 级需求的边界组至少有 **≥2 组有区分度输入**（单点输入 = 实现可硬编码期望值刷绿）。

```python
# 性质断言 + 固定种子 + 记录实际输入
@pytest.mark.parametrize("amount", [0, 100, 1000, 99, 101])
def test_REQ_042_满100减20_边界(amount): ...
```

## 五、跨模块接口：CDC 双向契约测试（签发件，编码方只读）

跨模块交互的需求，冻结时必须同时签发**接口契约**（输入 schema / 输出 schema / 错误契约 / 副作用声明 / 幂等性 / 超时重试语义 / 权限要求 / SLO），并配套签发 **CDC 双向契约测试**：

| 方向 | 验证什么 | 谁写 |
|---|---|---|
| 提供方 → 消费方 | 提供方实现**满足**契约（消费方按契约调用能通） | 起草方（签发件） |
| 消费方 → 提供方 | 消费方**按契约**调用，不依赖提供方内部实现细节 | 起草方（签发件） |

- 契约测试是**签发测试代码的一部分**，编码方**只读**——禁改断言、禁跳用例、禁调预期值、禁删改名。
- 契约变更走**需求变更流程**，不是代码 PR 能直接改的。
- 探索模式产物豁免契约前置，但**不可进入生产路径**（探索产物必须带不可合并标记）。

## 六、红线（违反即打回）

1. **禁平凡断言**：非空 / 不抛异常 / 日志关键词 / 状态码 2xx 四类一律不合格。
2. **禁只断言"抛了异常"**：必须断错误类型与语义。
3. **禁测试内绕过**：吞异常 / 条件断言 / 跳断言。
4. **禁隐藏关键断言**：关键判据不得埋在辅助函数深处而测试名不反映。
5. **禁与实现方同源**：起草方不共享实现方基座模型、会话上下文或提示历史；不接触本轮实现与实现方自述。
6. **禁只写固定样本**：must 级需求须有随机/性质断言与 ≥2 组有区分度输入。
7. **禁改需求措辞**：需求模糊就回报提出方，不在测试里"自行解释"。

## 七、交付物（交给审查方 / 人类签发）

| 交付物 | 内容 |
|---|---|
| 验收测试文件 | 仓内真实路径 + 代码（满足可渲染约定） |
| 覆盖矩阵 | 需求ID × 场景（正常/边界/异常/并发）× 是否覆盖 × 对应用例名 |
| 边界覆盖矩阵 | 需求边界清单（哪几维）× 覆盖情况 |
| 副作用矩阵 | 契约声明的副作用 × 观测接口 × 断言位置 |
| 审查清单自检结论 | §二 七条逐条结论（通过/不通过 + 依据） |
| 随机化说明 | 随机维度、种子策略、性质断言点 |
| 签发记录 | 起草方 / 复检方 / 签发方 / 冻结版本（字段口径见 `skills/skill-requirement-battle/SKILL.md` §4.3） |

## 八、常见反模式

| 反模式 | 表现 | 正确做法 |
|---|---|---|
| 非空断言 | `assert result` | 断言到字段值 |
| 状态码断言 | `assert r.status_code == 200` | 断言响应体关键字段 + 副作用 |
| 单点输入 | 只有一个固定 fixture | ≥2 组有区分度输入 + 性质断言 |
| 隐藏断言 | 断言写在 `_check()` 里 | 关键断言显式写在测试体内 |
| 条件断言 | `if cond: assert ...` | 场景拆分，禁条件包断言 |
| 期望值硬编码拟合 | 只对测试里的那个值成立 | 性质断言 + 边界维度覆盖 |
| 副作用靠肉眼 | 跑完看日志说"应该发了" | 用 mock 记录 / 快照 diff 断言 |
