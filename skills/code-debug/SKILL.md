# 代码调试

## 执行流程

### 第 1 步：确认需要（调试前必做）

进入调试前，先确认故障信息和复现条件就位，缺则停下追问，不靠猜测推进。

1. **确认故障现象**：报的什么错、什么场景下出现、预期行为 vs 实际行为
2. **确认复现条件**：最小复现路径、触发输入、运行环境；无法复现的 bug 先和上报方确认复现步骤
3. **确认需求维度**：这个 bug 是"功能没实现/行为不符合预期"还是"报错崩溃"。前者是**需求符合性问题**——核对实际行为偏离了哪个 AC、设计本意应该是什么，不能只盯着报错；后者才是纯技术故障
4. **确认涉及范围**：故障在哪个模块、调用链上下游、可能受影响的依赖
5. **确认已有线索**：错误日志、stack trace、已知的可疑点、之前是否修过该模块
6. **信息不全则停下**：通过 human_interaction 向上追问，确认齐了再进入第 2 步

### 第 2 步：摸清现有实现（防重复修复、防破坏架构，调试前必做）

调研故障模块现有实现，需要得出以下结论：

- 调用链摘要：故障模块的调用链上下游、数据流、依赖方向
- 可复用项：现有代码里有没有已经正确处理该场景的函数/分支
- 接口契约：本模块对外接口的签名、入参出参、异常、调用约束
- 架构边界：本模块职责边界、依赖方向，修复会不会跨过模块边界乱改、破坏对外接口契约

### 第 3 步：复现与定位（最多 2 轮，只加诊断标记，禁止改代码）

按 coding_domain_rules.md §1.5 Bug修复安全执行。

1. **先写失败测试**：必须先写一个能复现该 bug 的测试，确认它失败。已有测试能复现则跳过这步。
2. **最小输入复现**：用最小的输入触发失败
3. 在报错分支加 print 标记
4. **确认 WHO 不只是 WHAT**：确认"是哪个对象/实例在执行"，而不只是"报了什么错"

### 第 4 步：追踪根因（最多 2 轮，只加诊断标记，禁止改代码）

1. 在构造函数加 `traceback`（limit=4）
2. 确认对象被创建了几次、由谁创建
3. 检查 fork/clone/rebuild 是否丢失依赖
4. **检查对象生命周期**：bug 通常在对象被重建时丢失属性，不在报错代码本身

### 第 5 步：修复根因

1. 修复**真正的根因**（不是症状）
2. 在**完整系统中验证**（不是只跑隔离测试——隔离测试通过 ≠ 系统正确）
3. 移除所有临时诊断代码（print/traceback 标记）

### 第 6 步：回归验证

1. 重新运行**全部测试**（包括之前通过的）
2. 添加回归测试防止同类问题复发
3. 复验失败测试：原来复现 bug 的测试现在应通过
4. 如果仍有失败 → 回到第 3 步（同方向最多 3 次，超过则切换假设）

## 修复熔断机制

当同一模块的 bug 在完整调试流程中被打回超过 **3 次**仍未解决时，触发熔断：

1. **立即停止调试**，不再尝试修复
2. 将熔断报告写入 `docs/working/circuit_breaker_report.md`，内容包含：
   - 模块名
   - 已尝试的修复方向和失败原因
   - 该模块的已知问题清单
   - 怀疑的架构根因（如职责不清、隐式耦合、状态管理混乱）
3. 调用 task_evaluate 标记熔断状态
4. **禁止继续调试**

## 调试核心规则

1. **自顶向下**：先确认"谁在执行"，再优化"怎么执行"
2. **隔离测试陷阱**：隔离测试通过 ≠ 系统正确，通过后仍失败应切换到全链路追踪
3. **追踪对象生命周期**：bug 通常在对象被重建时丢失属性，不在报错代码本身
4. **反制 confirmation bias**：同方向 3 次无效后强制切换假设
5. **诊断加分叉点**：在多态分叉点加标记，不是在具体实现内部
6. **修复后清残留**：必须移除所有临时诊断代码

## 规则

- Bug 修复任务必须先写失败测试再调试修复
- 必须在完整系统中验证修复，不能只依赖隔离测试
- 修复后必须移除所有临时诊断代码
- 同一模块 bug 反复修复超过 3 次仍未解决时，必须触发修复熔断
- 必须先搜现有测试文件，有现成测试能复现 bug 时优先复用，禁止另起炉灶
- 必须添加回归测试防止同类问题复发
- 如果输入包含 state_machine，测试必须覆盖所有状态和转换

## 成功标准

- ✅ 原来复现 bug 的失败测试现在通过
- ✅ 全部测试通过（含回归测试）
- ✅ Bug 修复后在完整系统中不再出现
- ✅ 有回归测试防止问题复发
- ✅ 无残留临时诊断代码

## 产出（填入编排执行报告）

```yaml
debugging:
  bug_summary: <一句话描述 bug>
  root_cause: <根因，含对象生命周期/耦合点等定位证据>
  failing_test: <复现 bug 的测试路径>
  fix_files: [<修改的源文件>]
  regression_tests: [<新增的回归测试路径>]
  verification: {isolated: passed, full_system: passed}
  circuit_breaker: {triggered: true|false, report_path: <if triggered>}
  iterations: <调试轮次>
```
