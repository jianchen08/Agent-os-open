# 项目任务流程

> **本技能是流程指引，不是逐条打勾清单**：按场景判断使用，遇不适用情况保持裁量，不机械执行。
> 流程骨架的顺序真值常驻于主控提示词「项目任务链流程」节；本文件承载各步骤的执行细节与参数，按需读取对应节，不另立骨架顺序。

## 适用场景

L1 组织和管理项目任务链（一个 app、一个游戏、一部网络小说等复杂长期任务）时加载本 skill。项目 = 真实文件夹 + 登记（projects 域），不是任务实体。

## 一、项目挂靠流程

1. **澄清需求**
2. **确认项目**：项目由用户在界面创建（新建任务表单选"挂靠项目"）或已存在——L1 向用户确认项目 ID 后，后续任务提交都传 `project_id=项目ID`（子任务系统自动继承，无需显式传）
3. **设置进度触发器**：使用 `trigger_setup` 设置定时触发器（详见下文）
4. **方案规划（自执行）**：按本技能「七、方案规划段（plan 态口径）」执行——讨论与定稿自你，调研照常外包；方案经用户明确确认后，用 `project_state`（action=transition, target_state=running, reason=定稿说明）申请过门（弹用户审批；状态闸细节见该节与 task_submit 工具描述）
5. **执行任务链**（过门后立即执行，无需询问用户）：
   - **直接传递方案路径**：不要自己读任务链再转述给下级，下级比你更专业，它自己会读。goal 中写明方案文档路径（如 `docs/{title}_solution.md`），让下级自行读取任务链并执行
   - 用 `file_read(fields=["task_chain"])` 只读取任务链中的**执行者列表**，用于检查所需 Agent 是否已存在
   - 缺失资源 → 触发资源准备流程创建
   - 等待资源就绪后，将方案路径提交给对应执行者
6. **项目任务链收尾**：任务链全部完成（含最后的端到端验证任务）后通知用户
   - **取消触发器**：任务链完成后立即使用 `trigger_setup(action="cancel", trigger_id="之前记录的ID")` 取消进度触发器
   - 项目的暂停/恢复/删除由用户在界面管理（projects 域），L1 不代操作

## 二、workspace 决策

| 场景 | workspace 填法 |
|------|---------------|
| 挂靠项目（project_id） | 不填——系统恒解析为项目文件夹（worktree 从项目仓库分叉） |
| 独立任务 + 用户明确指定某个目录 | 填该目标目录 |
| ⚠️ 系统内部路径（.ai_workspaces 等） | 禁止填写，只用于资源管理任务 |

## 三、进度触发器配置

使用 `trigger_setup` 设置定时触发器，定期检查项目任务执行进度。

| 配置项 | 值 |
|--------|-----|
| **触发间隔** | 15 分钟 |
| **最大触发次数** | 小型 32 次（约 8 小时）、中型 96 次（约 24 小时）、大型 288 次（约 3 天） |
| **触发动作** | 检查项目任务当前状态，对照速查表验证产出物是否已生成 |
| **共用触发器** | 已有相同间隔的活跃触发器时不要新建，用 update 延长其生命周期 |
| **超时处理** | 触发次数耗尽后任务链仍未完成 → 延长次数并通知用户 |
| **记录 trigger_id** | 任务链完成时用于取消 |

**停滞检测**：子任务运行超 1 小时时查看详细进度，下次触发对比是否有变化。有变化继续等，无变化按优先级处理：①注入提示引导恢复 ②分析错误尝试修复 ③多次无效再通知用户。

## 四、方案不可变原则与修订分级

方案准备阶段人类确认的方案稿是任务执行的**绝对标准**，确认后不可更改。
「可不可改」的判据 = **traces_to 追溯链**（任务级 AC 是否仍可完整追溯到现行方案级 AC）：

- **执行层修正**（traces_to 不断链）：失败任务重派、任务内执行方案调整、
  实现细节/性能优化/不改接口契约的重构——running 内直接做，改动记入方案总纲
  「变更记录」并通知用户；
- **方案层修订**（traces_to 断链：方案级 AC 增删改、功能范围、技术选型、架构
  模式级变更）：running 态**禁止边跑边改方案文档**，只许用 `project_state`
  （action=transition, target_state=plan，reason 附改动点+断链影响面+在途任务
  清单）申请回门（反向审批，可选在途处理：跑完冻结派发/立即停）；回 plan 态
  按「七、方案规划段」修订后经同一道门再审恢复 running；
- **细化细节可调整**：方案细化的粒度、实现步骤等细节可以在不违背方案核心的
  前提下调整（属执行层修正）；
- 追溯完整性由 task-chain-viewer 检查兜底：任务级 AC 对账方案级 AC，断链在
  任务链可视化中可见。

## 五、失败处理与工作空间规则

### 工作空间规则

- **资源管理任务**（提交给 resource_manager_agent）需要设置 `workspace="<项目根目录绝对路径>"`
- workspace 参数含义、子任务继承、inherit_workspace_from 等通用规则参见 task_submit 工具描述

### 失败处理原则

完整失败处理策略见 task_manage 工具描述。核心原则（必须遵守）：

- **优先抢救已有成果，禁止动辄重新提交**：任务失败（尤其合并失败）时，第一反应是"看失败原因 + 检查 worktree 有没有产出"，不是"重新提交"。子任务在 worktree 中完成的工作是真实产出，丢弃重做是最大浪费
- **合并失败用 resource_merge 合并**：子任务代码写好了但 worktree 合并冲突，用 resource_merge 工具（action=merge）将 worktree 变更合并到目标空间，禁止重新提交丢弃成果
- **有产出就抢救，无产出才重做**：worktree 有有效产出 → non_isolated 模式/continue 定向修复；无产出或完全错误 → 才重新提交（须继承原工作空间）

### 隔离模式区分

评估失败时的处理方式取决于子任务的隔离模式：

| 模式 | 失败特征 | 处理方式 |
|------|---------|---------|
| **non_isolated** | 改动已直接生效到原文件，评估失败只是验收指标问题 | 确认产出无误即可，不需要重新提交 |
| **isolated** | worktree 不会自动合并到目标空间 | ①手动用 resource_merge 合并 worktree 变更到目标空间，或②重新提交让评估通过后自动合并 |

### 角色特定原则

- **Agent 不可更换**：任务链中指定的 Agent 不可更换，任何情况下都不考虑换 Agent——执行者缺位时按「一、4 缺失资源」触发资源准备流程**创建该 Agent**（不是换用别的 Agent）；用户明确要求换执行者时，按「四、方案不可变原则与修订分级」判定修订级别处理（任务文件 executor 字段属方案产物），禁止自行更换
- **禁止跳步**：重新提交必须保持原流程位置不变
- **兜底**：多次处理仍失败后必须通知人类，不要自行放弃或绕过
- 人类确认无法解决 → 通知用户并停止派发后续任务

## 六、项目管理规则

- 只有所有子任务都成功完成且文件产出符合验收标准，且已通知用户后，任务链才算完成
- 收到通知后立即处理，不要攒着等全部完成
- 无依赖的子任务可以并行提交，有依赖的必须等前置完成
- **任务链完成需用户确认**：通知用户前必须确认产出符合验收标准，不能自行判断
- **项目内禁止裸提交**：项目生命周期内对项目文件夹的所有操作都必须作为挂靠项目的任务提交
- **项目=文件夹管辖权**：挂靠项目后，对项目文件夹的任何读写操作都必须走项目任务
- **关联工作时必须继承**：新任务与已有任务相关联时必须继承（优先 pipe+workspace，只能继承一个时至少 workspace，项目内任务间继承 pipe）；不相关则不需要

## 七、方案规划段（plan 态口径）

本节约束项目任务链的**方案规划段**（项目 `workflow_state = plan`）：讨论与定稿
主 agent 自执行，调研与执行外包。过门转 running 后本节不再适用，改按本技能
一至六节执行任务链。本节是纯骨架：只写过程不变量与领域规格查询口，领域方案
内容一律经第零步查询口外取。

**过程不变量（禁入任何模式包物料——五件是机械闸执法前提，任何模式包不得复写）**：

1. **过门语义**：plan → running 必经用户审批，审批即冻结——过门前方案是
   工作稿，过门后禁止边跑边改；
2. **修订分级与回门**：判据 = traces_to 不断链（执行层修正）vs 断链（方案层
   修订必须回门），唯一口径见「四、方案不可变原则与修订分级」，此处不重复；
3. **traces_to 追溯契约**：每个任务级 AC 带 `traces_to: AC-{方案级编号}`，
   可二值判定；追溯断链由 task-chain-viewer 检查兜底；
4. **产物职责边界**：档案区只放稳定真相（架构决策/API 契约/领域模型/世界观/
   数值公式），方案总纲只讲 why，任务文件自包含（拿到即可开工），职责不重叠；
5. **AC 机读可二值**：方案级 AC 总表用机读 YAML（id/title/must/category/
   verify_hint），任务级 AC 逐条可二值判定。

### 前置绑定（动笔前先做）

1. 确认 `project_id`（用户提供，或先 `project_create` 登记取得）；
2. 读项目登记确认 `workflow_state = plan`（running 态收到新需求 = 修订申请，
   按「四、方案不可变原则与修订分级」申请回门，禁止直接改方案）；
3. 工作空间基准 = 本轮 state `project_roots` 注入的项目根；所有产物路径
   **一律相对项目根**书写（`docs/project/…`、`docs/…`），通知用户时
   file_paths 同基准。

### 第零步：任务类型与领域规格查询

- **任务类型**（通用过程，四分）：技术实现型（精确方案+实施计划）/ 精确创意型
  （方向明确+多方案比选）/ 开放探索型（广泛调研+收敛）/ 开放创意型（发散+聚焦
  验证）。在初步方案文档开头标注。
- **领域规格三级查询**：
  1. 项目登记的 `mode_tags` 在场 → 直接给域集合（主域 = `default_mode`；
     该读取空缺时跳过此跳）；
  2. 按模式注册表查该域包的 `plan_spec` 声明（各域模式包 mode.yaml 注册；
     查不到 → 自然走下跳）；
  3. `resource_search(resource_type="skill", query="{领域关键词}")` 搜领域
     技能，命中后 file_read 读其 SKILL.md；
  4. 仍无 → `human_interaction` 请示用户确认方案框架。
- 选定规格后按其「方案内容框架」与「产出物拆分约定」组织方案与产物。

### 过程骨架（调研 → 讨论 → 定稿）

- 职责分界一句话：**讨论与定稿自己执行，调研与执行外包**；plan 态内只许派
  调研（research_agent）、环境准备（environment_setup_agent）与经用户确认的
  打样（产出仅作参考材料）；
- 调研**外包** `research_agent`（task_submit 携 `project_id`；goal 写调研目标
  +范围；复杂调研可并行多方向；必须声明 `file_check`，路径
  `docs/working/{title}_research_report.md`）；
- 读第零步选定的规格，按其框架形成初步方案写入 `docs/{title}_solution.md`
  【自己执行】；human_interaction（conversation 模式）通知用户：文件路径 +
  核心要点 2-3 句，**必须传 file_paths**；
- 与用户多轮讨论，主动细化模糊部分（实施细节、量化指标、结构划分），细化到
  可直接生成任务链；不确定的问题再派 research_agent 补充调研；每次修改后通知
  用户（必须传 file_paths）；重复直至用户明确确认，随后按产物契约定稿。

### 产物契约（两类产物 + 档案区）

定稿产出拆**两类产物 + 档案区**，职责不重叠（领域拆分细节按第零步选定的规格；
无规格时请示用户）：

1. **档案区 `docs/project/`**（稳定真相源）：架构决策、API 契约、领域模型/
   业务规则、世界观设定、数值公式——方案阶段由你直接写入；平铺不分子目录；
   禁止写入模块清单、目录树、代码示例。
2. **方案总纲 `docs/{title}_solution.md`**（**只讲 why**）：背景与目标、调研
   摘要、关键决策理由、方案级 AC 总表（机读 YAML：id/title/must/category/
   verify_hint）、测试蓝图（软件类必填：用户旅程表+影响矩阵表，验证方式留空）、
   变更记录。禁止装具体设计/接口签名/实施步骤。
3. **任务文件 `docs/tasks/`**（自包含）：每任务一个 md，frontmatter 含
   `task_id/task_name/executor/depends_on/status/acceptance_criteria`（任务级
   AC 带 `traces_to: AC-{方案级编号}`，可二值判定）；正文含目标 / 执行方案与
   设计（接口契约级，拿到即可开工）/ 验收标准 / 备注。按内容边界打包，禁止按
   分析→设计→实现→测试工序拆；**最后一个任务固定为端到端验证+修复**，执行者
   `container_verification_agent`。
4. **检查点 `docs/{title}_checkpoints.md`**：检查点设计（自动通过 / Agent 互审 /
   里程碑门控）。
5. **任务链可视化 `docs/working/{title}_task_chain.html`**：经 resource_search
   加载 bash_execute 后调用
   `python skills/skill-task-chain-viewer/scripts/generate_task_chain_html.py --title "{项目名}"`
   生成。**bash_execute 仅限此脚本**，禁止用于改码/测试/构建/git。
6. **方案可视化（可选，讨论期沟通图）**：讨论期需要结构图辅助沟通时，
   `file_read` 加载 `skills/diagram-design/SKILL.md`，按其流程产出 standalone
   HTML，`human_interaction` 传 file_paths 交用户查看。本步骤**可选**——
   不进定稿前自检清单、不是门禁项、不计入定稿产物；域特化图（人物关系图等）
   物料随各域包提供，不在本骨架登记。
7. **项目根 `AGENTS.md`（项目宪法）**：定稿时按本模板 schema 生成实例——
   它是**派生物**（修订回门同刀更新），禁手写第二真相源；与本仓根 AGENTS.md
   （开发协作者指令）同名不同物，行业惯例 = 项目根一份，agent 进场先读。
   五节 schema：
   1. **项目领域与方案规格引用**：`mode_tags`/`default_mode`（项目登记的
      模式集合与主域）+ 第零步选定的 `plan_spec` 技能名；
   2. **产物地图**：`docs/project/`=档案真相 / 方案总纲=只讲 why /
      `docs/tasks/`=任务链 / checkpoints / 任务链 HTML / `skills/`=播种技能
      （各节写相对路径与职责一句话，不重复存真相）；
   3. **AC 契约**：方案级 AC 总表机读 YAML（id/title/must/category/
      verify_hint）、任务级 AC 带 `traces_to` 规则；
   4. **门与修订边界**：plan→running 人审、修订分级与回门判据
      （traces_to 不断链=执行层修正 / 断链=回门）；
   5. **域附加约定摘要**：按第零步选定规格的域约定摘录（无则写「无」）。

**定稿前自检清单**（全过才算定稿）：两类产物 + 档案区齐全且职责不重叠；AC
总表机读可二值；每个任务级 AC 可 traces_to 方案级 AC；任务文件自包含；末位
验证任务在；任务链 HTML 生成成功；**项目根 `AGENTS.md` 存在且五节齐全、与
实际产物结构一致**（派生物对账，漂移即重生成）；存量项目存在 `.project/`
目录 = legacy 档案位置，提示用户迁移到 `docs/project/`（不自动搬移）。

### 过门（plan → running）

用户明确确认方案后：用 `project_state` 工具申请 `plan → running`（触发用户
审批，审批通过前禁止派发执行类子任务）。plan 态内只许派调研、环境准备与经
用户确认的打样；审批即冻结，过门后修订一律走「四、方案不可变原则与修订分级」。
