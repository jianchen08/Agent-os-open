# 代码自审

> **本技能是流程指引，不是逐条打勾清单**：按场景判断使用，遇不适用情况保持裁量，不机械执行。

## 用途

编码完成、提交 task_evaluate 之前，对本次改动的代码做**机械化检查**（物理保险 5 项）、**签发分离检查**（2 项）、**同刀治理债检查**（5 项）、**提交卫生检查**（1 项）与**超时面检查**（1 项）。机械项只跑确定性检查（工具能客观判定，不依赖"第二双眼睛"的逻辑判断），目的是拦截低级错误，省去对小改动派独立审查的开销。

**能力边界**：本技能覆盖机械检查、签发分离检查与同刀治理债检查。需求追溯、架构边界四问、AC 符合度判断仍需独立 code_reviewer_agent。

**怎么让门禁绿**：门禁红了要修的是实现与测试的错配，不是门禁本身。签发分离两项检查给的就是这套方法——应试优化检测定位"实现只在被断言行为上正确"的错配，验收测试只读核查守住"验收证据不由实现方改动"这条底线。

## 检查项（物理保险 5 项）

| 检查项 | 怎么查 | 判定 |
|--------|--------|------|
| 模块边界物理化 | 检查是否有跨模块非法导入（绕过公共接口直接访问内部实现，如 import `_` 前缀函数、直接访问内部属性） | 有则失败 |
| 架构约束测试 | 检查模块间依赖方向是否正确，是否存在循环依赖（用 grep import 链） | 有循环则失败 |
| 需求覆盖扫描 | 检查新增代码是否关联了需求来源（AC编号或需求描述），识别无需求的孤儿代码 | 有孤儿代码则失败 |
| 安全与风格Lint | 运行 ruff/flake8/mypy，检查空 catch、遗留 print/console.log、无需求 TODO、硬编码密钥 | 有 error 级则失败 |
| 冗余模式检测 | 检测重复代码、翻译式注释、无效错误处理、死代码 | 有则失败 |

## 检查项（签发分离 2 项）

任务书携带签发验收测试时，本组检查与上面 5 项并列——它们防的是"证据被自己污染"，不是代码风格。

| 检查项 | 怎么查 | 判定 |
|--------|--------|------|
| 应试优化检测 | 实现是否只在被断言行为上正确：按 coding_domain_rules §6.5 口径执行泛化性自检（用测试集之外的同契约输入验证实现）与删值实验（改疑似硬编码的期望值/路径常量，相关测试须变红）；并查实现中是否存在只为迁就断言而写的分支或短路 | 只在被断言行为上正确 = 失败 |
| 验收测试只读核查 | 本次改动是否动过签发验收测试：取任务书里的验收测试签发记录（测试路径 + 冻结版本），与本次改动集比对，断言、用例、期望值、跳过标记任一被改即命中 | 动了签发验收测试 = 失败 |

## 检查项（同刀治理债 5 项）

改动触线某模块（plugins/shared / kernel/crates / frontend/src）时，同刀核查对应治理债是否已清——AGENTS.md「触碰即清」制度的检查表承接，防靠记忆执行（提案 P-28：6 样本实测 5✅1⚠️，违例不可见即纪律随机化）。

| 检查项 | 怎么查 | 判定 |
|--------|--------|------|
| mypy 基线棘轮 | 本次触线的 Python 模块 mypy 错误是否不增；清了既有错误则同刀下调 `.github/mypy-baseline.txt` | 触线未核 = 失败 |
| pytest 失败基线 | 修好基线内既有红测试时是否同刀收紧 `.github/pytest-failure-baseline.txt`（只收真实修复的红） | 该收未收 = 失败 |
| 覆盖率棘轮 | 新代码是否带测试；diff coverage 是否达 100%（`[skip-diff-cov]` 逃生口须显式归因）；基线文件改动是否 commit 留归因 | 缺测试且无归属说明 = 失败 |
| 文件行数棘轮 | 触线存量超限文件是否同刀收敛（`file-length-baseline` 档位） | 触线未核 = 失败 |
| 无测试改动归属 | 改动无对应测试时是否显式说明归属（测试稳定性修复/纯文档/配置面等） | 无说明 = 失败 |

## 检查项（提交卫生 1 项）

| 检查项 | 怎么查 | 判定 |
|--------|--------|------|
| 碎片化提交 | 本次任务是否存在同一文档/同一工作流的多笔微提交（`git log` 本次改动范围） | 有 = 失败，收口说明归并；文档/设计迭代按 AGENTS.md「攒批提交」里程碑一笔 |

## 检查项（超时面 1 项）

| 检查项 | 怎么查 | 判定 |
|--------|--------|------|
| 超时层注册表同步 | 本次改动新增/移除/修改任何超时层（等待界、缺省档、声明键、派生面）时，是否同刀更新 `docs/working/超时注册表.md`（单一注册表，防"数不全超时点"复发——BUG-60→10-27 两次收口均漏层的教训）；涉嵌套的过 L2 校验器（`kernel/crates/api/src/timeout_nesting.rs`），涉 LLM 链的过 L3 公式门禁（`scripts/check_llm_call_timeout_formula.py`） | 新增超时层未同刀更新注册表 = 失败 |

## 执行流程

1. 用 `bash_execute` 跑 lint/类型检查工具（ruff、mypy 等）
2. 用 `enhanced_search` / grep import 链检查跨模块导入和依赖方向
3. 用 `enhanced_search` 扫描无需求 TODO、硬编码密钥、遗留 print
4. 任务书携带签发验收测试时：跑签发分离 2 项检查（应试优化检测 + 验收测试只读核查）
5. 改动触线 plugins/shared / kernel/crates / frontend/src 任一模块时：跑同刀治理债 5 项检查
6. 汇总结果，填写执行报告模板的「自审结论」章节

## 产出（填入执行报告）

```yaml
self_review:
  status: pass | fail        # 任一检查项失败 = fail
  module_boundary: {status: pass|fail, violations: []}
  architecture: {status: pass|fail, cycles: []}
  security_lint: {status: pass|fail, issues: []}
  redundancy: {status: pass|fail}
  exam_optimization: {status: pass|fail, findings: []}     # 应试优化检测
  signed_test_readonly: {status: pass|fail, findings: []}  # 验收测试只读核查
  governance_debt: {status: pass|fail, unhandled: []}      # 同刀治理债（触线模块时必填）
  must_fix_before_submit: []  # status=fail 时必填，列出必须修的问题
```

## 规则

- `status=fail` 时，`must_fix_before_submit` 中的问题必须全部修复后才能调用 task_evaluate
- 自审结果写入执行报告的「自审结论」章节，供编排器核对
- 自审覆盖机械检查与签发分离检查；本任务是否还需独立 code_reviewer_agent，由执行 Agent 根据风险分级标签判断（见执行报告模板）
- 应试优化检测与验收测试只读核查的判定对象是"证据是否可信"，不是"风格是否达标"——判定失败先查实现，再查测试
- 签发验收测试只读：自审阶段同样不得改动签发测试来让检查通过，冲突项回报起草方与签发方重签
