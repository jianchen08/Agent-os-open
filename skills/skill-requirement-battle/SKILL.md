# 需求对抗（Requirement Battle）

> **本技能是流程指引，不是逐条打勾清单**：按场景判断使用，遇不适用情况保持裁量，不机械执行。
> **本件是融合件**：底座（结构化七步 + 方案骨架）不在此复述，按指针读；本件只写仓内结构化产物之上的**对抗增量**（追问纪律、三道审查闸、签发记录、预绑定范围表）。

## 〇、定位与边界

- **谁用**：调度方（需求阶段的编排者），以及被派去做需求结构化的执行者。
- **什么时候用**：接到模糊需求要收敛成可二值判定的 AC；起草任务书；需求变更要重新冻结；复核别人交上来的需求结构化产物。
- **不做什么**：不写实现代码；不产出验收测试代码（那是 `skills/skill-acceptance-test-authoring/SKILL.md` 的事，且起草方须与实现方异构）；不替代人类拍板。
- **与既有件的关系**：本件是**融合**——底座复用仓内既有资产，本件只加增量，不另起一套结构化流程。

| 层 | 真源 | 本件的关系 |
|---|---|---|
| 结构化底座（七步） | `config/processes/requirement_structuring.md` | 引用，不复述 |
| 方案骨架 | `skills/skill-solution-software/SKILL.md` | 引用，不复述 |
| 对抗性措辞规则面 | `config/rules/per_domain/coding_domain_rules.md` §1.8（模糊化措辞黑名单）、§1.7（需求冻结与签发语义） | 引用词条与处置口径，不复制词表 |
| 人类交互载体 | 方案 §2.6（追问卡：AC 草稿文件 + 结构化选项） | 按其纪律落追问节奏 |

## 一、底座：结构化七步 + 方案骨架（读，不复述）

按 `config/processes/requirement_structuring.md` 走完七步，**不可跳过任何步骤**：

```
原始需求 → 功能点提取 → 模块归属分析 → 验收标准分解(按模块分组) → 状态机识别 → 边界场景补充 → 自检 → 传递
```

要点提醒（细节以底座文件为准）：

1. **功能点提取**：动词+宾语、条件分叉（"如果…则…"）、隐含行为三类都要捞，隐含行为（如"提交后"的 loading、"失败后"的 error 处理）最容易在 Battle 中被漏掉。
2. **模块归属**：分清内部功能 / 对外功能，标出跨模块依赖方向；AC 按模块分组，保证每组能独立交给一个编码任务。
3. **AC 分解**：每条必须能回答"通过/未通过"、必须描述**可见效果**、标 must/should/nice。实现级 AC 标 `traces_to: AC-{方案级编号}`。
4. **状态机**：覆盖初始/进行中/成功/失败/空数据/特殊态，转换写清触发事件、前置条件、可见效果。
5. **边界场景**：至少从集合/数值/字符串/时间/网络/并发六个维度各想一遍。
6. **自检**：底座 §1.7 的九条自检项逐条过。
7. **传递**：AC 清单（按模块分组）→ 编码方；模块间接口定义 → 编码方（作约束）；状态机 → 测试设计输入；边界场景 → 异常测试输入；每条实现级 AC 至少一个以 AC-ID 命名的测试。

方案层骨架（架构/技术选型/模块与接口/数据模型/测试策略/交付流程）按 `skills/skill-solution-software/SKILL.md` 走，**只出需求与契约级**结论（"做什么、对外的契约是什么"），不到实现步骤与伪代码。

## 二、追问方法论（Battle 节奏）

### 2.1 四条纪律

1. **一次一问**：一轮只抛一个问题，附推荐项与理由。多问并行会让回答散焦，也让人无法逐条确认。
2. **暴露隐藏假设**：把需求里未言明但影响判定的假设显式列出来逐条确认（例："提交后进入 loading"就是隐含假设）。假设不显式化，后面会变成"实现方自行裁量"。
3. **主动挑战模糊措辞**：命中黑名单或近似表达当场挑战，并给可判定的改写建议（黑名单词条真源见 `config/rules/per_domain/coding_domain_rules.md` §1.8，**本件不复制词表**，以免两处漂移）。
4. **禁接受"差不多"**：任何"差不多/基本/大致/应该没问题"式回答都不进 AC——按 §1.8 处置：命中即由提出方改写后再冻结。

### 2.2 预算与收敛

- **预算**：一次一问、带推荐项，全程 **≤5 轮**；超限自动转方案对比选择（开放 Battle 收敛为封闭决策）。
- **载体**：追问信息面走**文件**（AC 草稿文件实时累积，随时可展开），卡片只承载动作——候选答案点选 / 自由回复 / 进对话。
- **兜底**：信息不足到无法完成结构化时，**标记"信息不足" + 列缺失信息点 + 追问**，禁止猜测补齐、禁止编造 AC。

## 三、对抗性需求审查清单（冻结前必过三闸）

对抗性审查是博弈上移的主要防线，与"需求来源真实性"同级。三闸逐条过，任一闸命中即**不得冻结**。

### 3.1 闸一：模糊化措辞闸

| 项 | 内容 |
|---|---|
| 判据 | 逐条 AC 扫 `config/rules/per_domain/coding_domain_rules.md` §1.8 的模糊化措辞黑名单；命中即不合格 |
| 加严 | 每条 AC 必须能映射到**具体可观察结果**（返回值/状态/副作用/阈值），不得以主观程度词描述达标程度 |
| 处置 | 由**提出方**改写后再冻结；实现方不自行解释模糊措辞、不按"差不多"自行裁量实现范围 |
| 记录 | 审查记录写"措辞闸：通过 / 命中 N 条（含 AC-ID、原文、改写建议）" |

### 3.2 闸二：边界弱化 diff 闸（与上一冻结版本对照）

需求"进化"最常见的退化是**边界被悄悄删掉或改软**。本闸逐条与**上一冻结版本**对照，输出差异表：

| 需求ID | 边界维度 | 上一冻结版本判据 | 本次判据 | 差异类型 | 处置 |
|---|---|---|---|---|---|
| AC-007 | 数值上界 | 上限 1000 条 | 若干条 | **弱化** | 回退改回，或由人类显式批准并留痕 |

- **差异类型**判定：
  - `新增`——本轮新出现的边界（记理由，不是问题，但要在记录里说清为什么这轮才加）；
  - `删除`——上一版有、本版消失的边界条目（**高危**：需求没说要删，就是被删了）；
  - `弱化`——判据从具体阈值/集合/枚举变成模糊表达或范围缩小（例：上界 `1000` → `若干`；错误类型 `ValidationError` → `抛异常`）；
  - `保持`——两版一致。
- **处置规则**：`删除` 与 `弱化` 一律**回退到上一版判据**；确需变更的，由人类显式批准 + 在变更说明中写清理由与影响面；**禁止默认接受**（"看起来无所谓"是弱化的一种，不是理由）。
- **对照对象**：上一冻结版本的 AC 清单与边界场景清单。首版需求无上一版时，本闸记"无对照基线（首版）"，不省略。

### 3.3 闸三：断言删减/放宽闸（同一需求ID下的签发测试）

需求弱化会连带签发测试一起松。对同一需求ID，比对上一版与本版的签发测试：

| 需求ID | 上一版用例/断言 | 本版用例/断言 | 变化 | 处置 |
|---|---|---|---|---|
| AC-007 | `test_..._upper_bound` 断言 1001 条报错 | 用例删除 | **删除** | 与需求变更无关 → 回退；有关 → 逐条对应进变更说明 |

- **变化类型**：删除用例 / 断言放宽（具体值 → 非空、类型 → `Exception`、集合 → 长度非零）/ 断言改指向 / 场景组整体丢失。
- **处置规则**：与需求变更无关的删减/放宽**一律回退**；确属需求变更导致的，必须在变更说明里**一一对应**（哪个需求变更导致哪条断言变化），对应不上的视为弱化。
- **执行方约束**：签发测试对实现方**只读**——禁改断言、禁跳用例、禁调预期值、禁删改名（真源见 `config/rules/per_domain/coding_domain_rules.md` §1.7）。本闸查的是"测试侧有没有被改松"，不是"实现有没有改对"。

## 四、冻结产物（四件套）

冻结即签发：需求冻结不是文档版本锁定，而是**验收测试代码签名锁定**。冻结时必须同时产出：

### 4.1 AC 清单（按模块分组）

每条含：AC-ID（稳定、不可复用）、需求描述、可二值判定的验收判据、优先级（must/should/nice）、`traces_to`（方案级 AC 编号）、所属模块。**must 级 AC 必须有签发测试覆盖**——无签发测试的关键路径 AC 视为未冻结。

### 4.2 状态机 + 边界场景清单

按底座七步产出，一并冻结（下游测试设计的输入）。

### 4.3 验收测试签发记录

| 字段 | 说明 |
|---|---|
| 需求ID | 一条 AC 一行 |
| 验收测试文件路径 | 签发测试在仓内的真实路径 |
| 起草方 | 谁写的测试代码（AI/人类）；须与实现方**异构**（不同基座模型/不同会话上下文） |
| 签发方 | 人类（签发权与 diff 确认权留人类） |
| 冻结版本 | 版本号/提交号 |
| 审查清单结论 | 起草方自检 + 审查方复检的逐条结论（清单见 `skills/skill-acceptance-test-authoring/SKILL.md`） |
| 渲染规格页 | 人类读的渲染投影路径（可选） |

### 4.4 预绑定范围表（需求ID ↔ 允许变更范围）

| 需求ID | 允许变更的文件/接口 | 禁止触碰 | 依赖的需求ID |
|---|---|---|---|
| AC-007 | `src/foo/bar.py`、`foo.bar()` 签名 | 其他模块内部实现、公共基类 | AC-003 |

- **用途**：编码方**只能**在绑定范围内操作，超出即阻断；不得事后自报"这行对应需求X"。
- **粒度**：到文件与对外接口签名，不到行。
- **与改动面绑定表的关系**：本表是需求侧的绑定事实，落地为任务书里的改动面绑定表，是范围一致性检查的输入。

## 五、交接与只读边界

| 下游 | 交付什么 | 下游能做什么 |
|---|---|---|
| 验收测试起草方 | 冻结 AC + 状态机 + 边界场景 + 契约 | 起草验收测试；**看不到**实现与实现方自述（防反向适配） |
| 编码方（实现） | 预绑定范围表 + 签发测试路径 | **只读**：不新增/不改写/不解释需求措辞，不改签发测试断言 |
| 审查方 | 冻结产物全套 + 变更对照表 | 盲审：只认冻结规约与独立测试结果 |

## 六、红线（违反即回退）

1. **需求冻结后只读**：实现方不得改写、不弱化、不"就地澄清"后按改写版实现；发现需求与实现冲突，**回报提出方/调度方裁定**。
2. **禁编造**：信息不足时追问，不猜、不编 AC。
3. **禁越界承诺**：不得新增方案未承诺的功能；实现级 AC 只能细化方案级 AC。
4. **禁把弱化当优化**：边界删除/弱化、断言放宽一律回退，除非人类显式批准并留痕。
5. **禁自产验收证据**：本件的产出是需求与绑定，不是验收证据；验收证据来自签发方或独立复核方。
6. **禁自动接受人类卡**：连续无修改签发会触发抽检复核，"点通过"不等于"评审通过"。

## 七、常见反模式

| 反模式 | 表现 | 正确做法 |
|---|---|---|
| 多问并行 | 一轮抛五个问题，人只答了第一个 | 一次一问 + 推荐项 |
| 隐含假设不显式 | 实现方自行补"提交后 loading" | 假设逐条列出让人确认 |
| 弱化当精简 | "上界 1000 改成若干，反正没人测" | 走闸二，回退或显式批准留痕 |
| AC 只写功能不写可见效果 | "支持导出"无法判定 | 写可见效果 + 可观察结果 |
| 签发记录缺字段 | 只有路径没有签发人/版本 | 签发记录七字段齐全 |
| 预绑定范围过粗 | 绑定到目录级 | 绑定到文件 + 对外接口签名 |
