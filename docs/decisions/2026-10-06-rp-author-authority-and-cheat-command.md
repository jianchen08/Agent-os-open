# ADR 2026-10-06：作者权威（Author Authority）+ 作弊显式命令

## 背景

之前 ADR（`2026-10-06-rp-two-axis-mode-spectrum.md`）提出"二轴谱"：
- 轴 1：LLM 可用性（with/without）—— 玩家可切
- 轴 2：规则复杂度（none/core/full）—— 设计上**玩家可切**

用户反馈指出关键问题：

> "不对不是用户是否启用更严格的规则，而是作者声明，而如果用户想要作弊不是启用规则与否二十命令。"

**问题**：让玩家运行时切换 `rule_complexity`（比如从 `core` 切到 `none`）实际上**让玩家能轻易作弊**。这破坏了"代码层校验"的反作弊价值，违反了游戏规则作者设的规则。

之前的 `§0.5 合法切换路径` 列了"`core ↔ none`"让玩家主动关闭引擎，这是错的。

## 决策

**作者拥有规则权威**——`rule_complexity` 与 `contract_level` 是作者在创建角色卡时**一次性声明**的，**玩家不可运行时切换**。

**作弊是显式命令，不是模式开关**——如果玩家想绕过规则，必须输入 **`/cheat` 命令**（per-task 一次性状态变更，可审计）。

### 权力分布

| 谁 | 轴 1（LLM 可用性） | 轴 2（规则复杂度） |
|---|---|---|
| **作者**（在角色卡 YAML 创作期） | ✓ | ✓ |
| **玩家**（运行时） | ✓（LLM 健康度 / 主动离线） | ✗ **禁止** |
| **`/cheat` 命令** | — | 一次性覆盖（可审计） |

### 关键修正点

**修正前**：§0.5 列了 `core ↔ none` 让玩家切到「LLM 全权」afengy 模式 —— 这是错的。

**修正后**：
- `core ↔ none` 不能由玩家切 —— `none` 模式只能由作者在创作时设
- 玩家要"作弊到 afengy 模式"必须用 `/cheat`
- 作弊状态会留痕（审计日志、成就排除）

### 角色卡字段新增

```yaml
character_card:
  engine:
    rule_complexity: "core"      # 作者声明，玩家不可改
    allow_cheat: true           # 作者是否允许玩家作弊？默认 true
    llm: "with_llm"             # 作者声明，玩家可切
    contract_level: 2           # 作者声明，玩家可调 ±1 用于观感
```

### 作弊命令语义

```bash
/cheat                # 启用作弊（默认 on）
/cheat on             # 同上（明确）
/cheat off            # 关闭作弊（恢复作者规则）
/cheat status         # 查看当前状态（是否作弊、规则严格度等）
/cheat allow          # 玩家恢复作弊（如被锁）
/cheat deny           # 关闭作弊
```

**触发流程**：

1. 玩家输入 `/cheat`
2. 系统检测：
   - `engine.allow_cheat == false`？→ 拒绝 + 提示
   - `engine.allow_cheat == true`？→ 进入确认流程
3. 弹出确认对话框（防误操作）：
   > "您即将禁用本游戏的所有规则校验。本次操作将记入审计日志。作者与平台可在审计日志中查看此操作。确认启用吗？"
4. 玩家确认
5. `state.meta.cheating = true`（写入 task_id metadata）
6. `audit_log.append({ type: 'cheat_enabled', task_id, user_id, timestamp })`
7. 前端右上角显示红色 "本会话已作弊" badge
8. 后续所有引擎校验被旁路（但仍落 log）
9. 后续所有 LLM 提议的 state_changes 被允许（不再 clamp）
10. 后续所有 actions 直接执行（不再校验）
11. 后续 narrative_graph 的触发器全部失效（玩家自由）

### 作弊 ≠ 完全自由

| 维度 | 作弊前 | 作弊后 |
|---|---|---|
| 规则代码 | 仍执行 | 仍执行但旁路校验 |
| 状态机 | 仍记录 | 仍记录但允许超界 |
| 审计日志 | 全程留痕 | 全程留痕（含作弊动作）|
| LLM 全权 | ✗ | ✓ |
| 数据持久化 | ✗（可保存）| ✓（可保存但带 [audit: cheat] 标签）|
| 排行榜/成就 | 正常 | **排除**（作弊玩家的成就不上墙）|
| 多人同步 | 正常 | 同步给同任务玩家（看得到 "X 已作弊"）|

### 为什么不让作弊"完全自由"

1. **审计必须留痕** —— 否则破坏 RP 生态的信誉（参考电子游戏的金手指/作弊码会被记录）
2. **成就要排除** —— 否则作弊玩家可以刷榜
3. **数据不污染** —— 作弊 session 可被识别、回滚、隔离

### 作者对作弊的额外控制

```yaml
character_card:
  engine:
    rule_complexity: "full"
    allow_cheat: false              # 作者明确禁止作弊（敏感内容/严肃剧情）
    
    # 或：作者可以精细控制哪些规则在作弊时被保留
    cheat_overrides:
      keep_state_machine: true       # 即便作弊，HP 仍然走代码
      keep_inventory: true           # 物品仍然强校验
      bypass_narrative_graph: true   # 但叙事图触发器失效（玩家可自由选节点）
      bypass_state_validation: true    # 校验失效
```

**为什么有些规则作者会想保留**：严肃剧情（如角色死亡不可逆）的作者希望：即便玩家作弊，HP 归零仍是死亡，不能复活。

## Alternatives Considered

### A. 玩家运行时切换 `rule_complexity`（之前的设计）

- 优点：UI 友好
- 缺点：**玩家可作弊**（从 core 切到 none 来绕过校验），破坏作者规则权威
- 否决理由：用户反馈明确指出这是错误的

### B. 完全禁止玩家切换（连 `with/without_llm` 也不行）

- 优点：完全锁定
- 缺点：LLM 健康度低时无法降级，玩家无法主动离线
- 否决理由：`llm` 轴关乎可用性（技术性），与游戏规则无关，应该可切

### C. 作者权威 + 作弊显式命令（采纳）

- 优点：
  - 尊重作者规则权威（与游戏设计主流一致）
  - 作弊可审计（生态健康）
  - LLM 可用性仍可切（不破坏可用性）
- 缺点：
  - 玩家不能"自由切换严格度"（学习成本略高）
- 缓解：
  - UI 上显示"作者规则：strict/coreful/loose" badge
  - `/cheat` 命令简单明了

### D. 没有 `/cheat`，完全强制规则

- 优点：作者权威最大化
- 缺点：玩家想要"剧情向自由聊天"会被严苛规则卡住（不友好）
- 否决理由：与 RP 文化不符（很多创作者希望玩家用 vs 不被规则约束）

## 影响

### 正面

- **作者规则权威确立** —— 创作者知道自己的规则不会被玩家绕过
- **作弊生态健康** —— 留痕 + 成就排除，防止"作弊玩家刷榜"
- **LLM 可用性不受影响** —— 玩家仍可切 with/without_llm
- **数据完整性** —— 作弊 session 可被识别、回滚

### 负面

- **学习曲线** —— 玩家从 ST 迁来需要适应"作者规则不能切"
- **作者需考虑 allow_cheat** —— 默认 true，需要明确写 false 才能禁止

### 中性

- 与 ST 的兼容：ST 用户习惯"自由切模式"，迁移需要适应
- 与 afengy 的兼容：afengy 用户习惯"完全自由"，可能不适应
