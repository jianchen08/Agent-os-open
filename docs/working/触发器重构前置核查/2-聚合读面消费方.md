## 0. 读面现状语义（基线）

`handle_pipeline_state_list`（kernel/crates/api/src/capability_router.rs:2070-2200）三层数据：
1. 内存 registry 热行（:2081-2103，按租户过滤，`summarize_state` 经 `export_fields` 出口白名单裁剪 + `source:"memory"`）；

## 2. 结论与决策项

### 2.1 高危约束：终态判定消费方要求"终值不被 staged 遮蔽"（P3/P11，旁及 P4）

stop_check 的执行语义是"任务终态当轮停止"（用户裁定，plugin.py:24-31 注释自证），review 复盘轮询同构。合并视图若采用 **staged 覆盖 committed** 的字典序，且过程态迁移沿用 `task.status` 命名空间（现状 task_evaluate 经 update 写 `task.status=evaluating`，见 server.py:42-46 注释），则 committed 终值（completed/failed）会被 staged 残留中间值遮蔽：最坏情形终态检测延迟一轮（staged 易失、边界收编即清），若收编链路再把中间值写回 committed 则空转回归。三选一约束（任一即可）：
1. 合并序 committed 覆盖 staged（对状态类键）；
2. 过程态暂存键离开 `task.*` 命名空间（如 `eval.*`），终值键绝不入暂存；
3. 读面按来源区分（行加 `source`/键加视图标记），终态判定消费方只读 committed——但CapabilityCaller 无参数区分，需 handler 内建策略。

### 2.2 语义受益方：CONDITION 求值（P1）与评估输入（P2）

合并视图正是 GAP-2 的目标语义（trigger-eval-unification ADR :7："state 任意位置命中即执行"需要 staged+committed 两观察视图）。注意 ADR 决策 1/3：求值上收内核 trigger-svc、触发器声明 watched 视图防双触发——插件侧合并视图是过渡形态，`load_from_state`（P1 重灌）应仍以 committed 的 `task.trigger.registry.*` 为准。

### 2.3 无感知方（结构键/基线键消费，占多数）

P6-P9、P12、P13（pipeline_id/thread_id/agent_id/lineage.\*/task.owned.\*/task.parent_project_id/mode.\*/ws_meta/raw_result）+ K6/K7 + F2/F3：staged 层按已有管道键控、不产生新行、不落这些键 → 无感知。

### 2.4 决策项：capability 与 HTTP 两读面是否同步翻语义

routes.rs:1236-1239 明示 GET /pipelines/state 与 pipeline-state.list 共用出口语义（同款 summarize/补齐/冷兜底）。只改 capability 会造成"插件看到的 state ≠ 前端看到的 state"。建议同批翻转（前端 F1 的视图模型映射单点可吸收未知键，风险低）或在 ADR 明示 HTTP 面保持 committed 及理由。

### 2.5 退役 update 的配套机械点（非读面）

plugin-loader/registry.rs:640 方法表收敛 `&["list"]`（K3）；mcp STANDARD_CAPABILITIES 键名不动（K2）；invoker G6 授权面与对应测试随声明制收敛（K4）。

### 2.7 统计

- 消费方点位合计：内核 Rust 8（K1-K8，其中 K4 为测试、K6/K7 为 registry 直读非 capability）+ HTTP/前端 4（K5/F1-F3）+ Python 14 组（P1-P14，覆盖 21 个授权/消费插件：15 个 manifest 显式 granted pipeline-state + 6 模式面板共宿消费 + 四通道共用 channel_common）。
- 高危：P3 stop_check（执行语义：终态当轮停止）；次高危：P11 review、P2 task_evaluate（语义需确认）、K5/F1 两读面分叉决策。
- 其余全部无感知或低危（结构键消费 / 展示面实时性提升）。
