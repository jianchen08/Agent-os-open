### 1.1 Agent 工程师面试的四大考察维度

基于牛客网、知乎、脉脉等平台 2024-2026 年真实面经汇总，AI Agent 工程师面试的考察维度和权重分布如下：

## 二、各公司面试风格与代码要求

### 2.1 代码面试要求分级

基于面经统计，各公司对"手撕代码"的要求差异很大。对陈健来说，**选择对代码要求相对宽松的公司作为突破口**是关键策略：

| 代码要求等级 | 公司 | 手撕代码情况 | 应对策略 |
|-------------|------|-------------|----------|
| 🔴 **硬性要求** | 字节跳动、百度、腾讯 | 每轮必考，LeetCode 中等难度，45分钟限时 | 必须刷够 LeetCode 热题 100，优先准备 |
| 🟡 **有但可协商** | 阿里（部分部门）、MiniMax、零一万物 | 有代码环节但偏工程实现题（如写一个简单的 RAG、实现工具调用） | 工程题比算法题更有优势，展示项目代码 |
| 🟢 **侧重系统设计** | 智谱 AI、月之暗面（Kimi）、DeepSeek | 更看重架构思考、项目深度、Agent 理解，代码环节少或可选 | **优先投递**——灵汐项目价值最大化 |
| 🔵 **侧重产品/场景** | 百川智能、出门问问、垂直领域 AI 公司 | 关注落地能力和场景理解，代码要求低 | 适合作为保底选择 |

### 2.2 各公司面试特点详析

#### 🔴 字节跳动（豆包/Coze 团队）
- **风格**：算法硬性门槛，过不去直接挂，不讲情面
- **代码题**：一面必考 LeetCode 中等，二面可能考 Hard；也可能考 Agent 相关编码（如实现一个简单的 ReAct 循环）
- **Agent 考点**：RAG 优化、Prompt Engineering、多轮对话管理、Tool Use 设计
- **建议**：放在冲刺轮，算法刷够再投

#### 🟡 阿里（通义/钉钉 AI 团队）
- **风格**：看部门，搜索推荐团队偏算法，应用开发团队偏工程
- **代码题**：可能考 LeetCode 简单-中等，也可能考"手写一个简易 RAG pipeline"
- **Agent 考点**：系统设计能力、工程化实践、大规模场景优化
- **建议**：选择应用开发岗位，避免纯算法岗

#### 🔴 百度（文心一言团队）
- **风格**：算法基础扎实是基本要求，面试偏理论
- **代码题**：一面手撕算法（中等），可能追问时间空间复杂度
- **Agent 考点**：Transformer 细节、Attention 变体、LLM 训练流程
- **建议**：需要扎实的理论基础，放后期投递

#### 🔴 腾讯（混元/微信 AI 团队）
- **风格**：一轮笔试（算法+系统设计），二三轮技术面
- **代码题**：笔试有编程题，技术面可能现场写
- **建议**：算法刷够再投

#### 🟢 智谱 AI
- **风格**：技术驱动，重视对 LLM 和 Agent 的深度理解，面试偏讨论式
- **代码题**：有但不是核心筛选标准，更看重思路和技术直觉
- **Agent 考点**：大模型原理、Agent 框架设计、RAG 策略、对 GLM 系列模型的理解
- **建议**：**优先投递**——灵汐项目的自研架构是核心卖点

#### 🟢 月之暗面（Kimi）
- **风格**：创业公司节奏，面试偏实战，关注解决问题能力
- **代码题**：可能考工程实现题（写一个简单的文档检索+问答），不太考纯算法
- **Agent 考点**：长文本处理、RAG、Prompt 设计、产品思维
- **建议**：**优先投递**——长文本处理和灵汐的记忆系统有天然衔接

#### 🟢 DeepSeek
- **风格**：极客文化，重视技术深度和独立思考
- **代码题**：有但偏工程/研究导向，不太考标准 LeetCode
- **Agent 考点**：模型原理、推理优化、Agent 系统设计
- **建议**：**优先投递**——自研框架的经历非常加分

#### 🟡 MiniMax
- **风格**：产品导向，重视落地方案
- **代码题**：有编码环节，偏工程实现
- **Agent 考点**：多模态、Agent 应用落地、用户体验
- **建议**：中等优先级

### 维度一：LLM 原理与基础

#### Q1 ⭐ 【Token 与 Context Window】
**问题**：请解释什么是 Token？为什么不同模型的 Tokenizer 不同？Context Window 是什么，它对 Agent 系统设计有什么影响？

**参考答案要点**：
- Token 是 LLM 处理文本的最小单位，不等于字符也不等于词
- 不同模型使用不同分词算法：GPT 用 BPE，BERT 用 WordPiece，LLaMA 用 SentencePiece
- Context Window 是模型一次能处理的最大 Token 数（如 GPT-4 是 128K，Claude 是 200K）
- 对 Agent 的影响：对话历史管理（截断/摘要）、RAG 检索的 chunk 大小选择、多轮对话的上下文压缩策略
- **灵汐印证**：灵汐的 context_compressor.py 和 history_buffer.py 就是为了解决 Context Window 限制

#### Q2 ⭐⭐ 【Transformer 与 Attention】
**问题**：请用直觉语言解释 Self-Attention 机制。为什么 Transformer 用多头注意力（Multi-Head）而不是单头？

**参考答案要点**：
- Attention 本质是"加权查字典"：Query（你的问题）与 Key（字典条目）计算权重，对 Value（条目内容）加权求和
- Self-Attention 的特殊之处：Q、K、V 都来自同一个输入序列，让每个位置"看向"其他所有位置
- 多头注意力的意义：不同头关注不同模式（语法关系、语义关联、位置信息等），类似"多个专家从不同角度分析"
- 核心计算公式直觉：softmax(QK^T / sqrt(d)) V
- **灵汐印证**：虽然灵汐不涉及模型训练，但理解 Attention 是理解 Embedding 和语义检索的基础

#### Q3 ⭐⭐⭐ 【RAG 完整流程与优化】
**问题**：假设让你设计一个企业知识库问答系统，请描述完整的 RAG 流程，并说明每个环节可能的优化点。

**参考答案要点**：
- **完整流程**：文档加载、文档切分（Chunking）、向量化（Embedding）、存入向量数据库、用户提问、Query 向量化、向量检索、上下文组装、LLM 生成回答
- **各环节优化**：
  - 切分：按语义边界切分（不只是固定长度），保留重叠（overlap）
  - Embedding：选择领域适配的模型，考虑 fine-tune Embedding 模型
  - 检索：混合检索（向量 + 关键词 + BM25），重排序（Reranker），查询改写
  - 上下文：控制注入量，去重，按相关性排序
  - 生成：Prompt 模板优化，引用溯源
- **灵汐印证**：灵汐的 retriever.py 实现了 RRF 混合检索，semantic_preprocessor.py 做语义预处理

### 维度二：Agent 架构与核心概念

#### Q4 ⭐ 【Agent 的本质】
**问题**：什么是 AI Agent？它和普通的 LLM 对话有什么本质区别？

**参考答案要点**：
- Agent = LLM + 记忆 + 工具 + 规划 + 自主决策
- 本质区别：Agent 有"行动力"——能调用工具、维护状态、自主决定下一步
- 核心循环：感知（输入）、思考（LLM 推理）、行动（工具调用）、观察（结果反馈）、循环
- 普通 LLM 对话是"单轮问答"，Agent 是"持续行动的循环"
- **灵汐印证**：灵汐的管道引擎就是这个核心循环的工程化实现—— while not ended: Input / Core / Output / Route

#### Q5 ⭐⭐ 【ReAct 模式与 Agent 循环】
**问题**：ReAct（Reasoning + Acting）模式是什么？它和 Plan-then-Execute 有什么区别？各自的优缺点？

**参考答案要点**：
- **ReAct**：交替推理和行动，每一步先 Thought（思考），再 Action（执行工具），再 Observation（观察结果），然后继续
- **Plan-then-Execute**：先生成完整计划，再逐步执行，执行中不修改计划
- **ReAct 优点**：灵活，能根据中间结果调整策略；**缺点**：可能跑偏，缺乏全局视野
- **Plan-then-Execute 优点**：有全局规划，步骤清晰；**缺点**：无法应对意外情况
- **灵汐印证**：灵汐的 L1（主任务规划）= Plan，L2（子任务执行）= Act，L3（原子操作）= 具体动作

#### Q6 ⭐⭐⭐ 【Multi-Agent 编排设计】
**问题**：如果让你设计一个"软件开发 Agent 团队"（包含产品经理、程序员、测试员），你会怎么设计架构？Agent 之间如何通信和协调？

**参考答案要点**：
- **架构选择**：主从架构（Orchestrator 模式）vs 去中心化协作（Swarm 模式）
- **推荐 Orchestrator 模式**：一个主 Agent 负责任务分解和协调，子 Agent 负责具体执行
- **通信方式**：共享状态 + 消息传递；主 Agent 维护全局任务看板
- **工作流**：产品经理 Agent 输出需求文档、程序员 Agent 输出代码、测试员 Agent 输出测试报告、主 Agent 汇总决策
- **关键设计点**：任务依赖管理、错误处理（一个 Agent 失败怎么办）、上下文传递
- **灵汐印证**：灵汐的 L1/L2/L3 三层编排 + 跨管道路由 + 消息总线就是这个问题的工程实现

### 维度三：工具调用与 MCP

#### Q7 ⭐ 【Function Calling 机制】
**问题**：OpenAI 的 Function Calling 是怎么工作的？LLM 本身能执行函数吗？

**参考答案要点**：
- **关键认知**：LLM 本身**不执行**任何函数，它只是输出一个结构化的"函数调用意图"（函数名 + 参数的 JSON）
- **完整流程**：
  1. 开发者在请求中声明可用函数列表（JSON Schema 描述）
  2. LLM 判断是否需要调用函数，如果需要，输出函数名和参数
  3. 开发者解析 LLM 输出，在本地执行函数
  4. 将函数结果作为新的消息发回给 LLM
  5. LLM 基于函数结果继续生成回答
- **本质**：LLM 充当"决策者"，外部系统充当"执行者"
- **灵汐印证**：灵汐的 tools/executor.py 就是这个"执行者"

#### Q8 ⭐⭐ 【MCP 协议】
**问题**：什么是 MCP（Model Context Protocol）？它解决了什么问题？和 Function Calling 是什么关系？

**参考答案要点**：
- **MCP 是什么**：Anthropic 提出的开放协议，标准化 LLM 应用与外部工具/数据源的连接方式
- **解决的问题**：每次集成一个新工具都要写定制代码，MCP 提供统一标准——类似"AI 的 USB 接口"
- **核心概念**：MCP Server（提供工具的服务端）、MCP Client（消费工具的客户端）、Tools/Resources/Prompts
- **与 Function Calling 的关系**：Function Calling 是 LLM 调用工具的"信号格式"，MCP 是工具注册和传输的"通信协议"，两者互补
- **灵汐印证**：灵汐已实现 tools/mcp_client.py 和 mcp-servers/ 目录，同时作为 MCP Client 和 MCP Server

#### Q9 ⭐⭐⭐ 【工具系统设计】
**问题**：设计一个 Agent 工具系统，需要支持工具注册、参数校验、执行超时、结果缓存、权限控制。请描述核心架构和关键设计决策。

**参考答案要点**：
- **注册中心**：工具元数据管理（名称、描述、参数 Schema、权限等级、缓存策略）
- **参数校验**：JSON Schema 验证 + 输入归一化（处理 LLM 输出的格式不一致问题）
- **执行引擎**：异步执行 + 超时控制 + 进度回调 + 错误策略（Abort/Skip/Retry/Fallback）
- **缓存层**：幂等工具的结果缓存（TTL 策略）
- **权限控制**：基于 Agent 层级的工具访问控制（L3 只能用安全工具，L1 可以用所有工具）
- **灵汐印证**：tools/registry.py（注册）、tools/executor.py（执行）、tools/input_normalizer.py（归一化）、tools/tool_cache.py（缓存）

### 维度四：记忆系统与 RAG

#### Q10 ⭐ 【Agent 记忆分类】
**问题**：Agent 的记忆分为哪些类型？各自的用途和实现方式是什么？

**参考答案要点**：
- **短期记忆（工作记忆）**：当前对话上下文，存储在消息列表中，受 Context Window 限制
- **长期记忆（情景记忆）**：历史对话摘要、用户偏好，存储在数据库中，通过检索注入
- **语义记忆（知识库）**：外部知识文档，通过 RAG 检索注入
- **实现方式**：短期=对话消息列表；长期=向量数据库 + 关键词检索；知识=RAG pipeline
- **灵汐印证**：灵汐的 memory/service.py 实现了三层决策模型——情景记忆（EpisodeService）、语义记忆（KnowledgeService）、检索器（IRetriever）

#### Q11 ⭐⭐ 【向量检索与混合检索】
**问题**：纯向量检索有什么问题？什么是混合检索？RRF（Reciprocal Rank Fusion）是怎么工作的？

**参考答案要点**：
- **纯向量检索的问题**：对精确关键词匹配差（如产品编号、人名），语义相似但不相关的结果噪声大
- **混合检索**：同时使用向量检索（语义相似）和关键词检索（精确匹配），合并结果
- **RRF 工作原理**：
  - 向量检索返回排序列表 R_v，关键词检索返回排序列表 R_k
  - 对每个结果，RRF 得分 = Σ 1/(k + rank)，k 是常数（通常60）
  - 按 RRF 得分合并排序
- **优势**：不需要归一化不同检索方法的得分，天然处理得分尺度差异
- **灵汐印证**：灵汐的 memory/retriever.py 中的 RRFMerger 就是这个实现

#### Q12 ⭐⭐⭐ 【上下文压缩与注入策略】
**问题**：在长对话场景下，如何管理上下文避免超出 Context Window？请描述至少三种策略及其适用场景。

**参考答案要点**：
- **滑动窗口**：保留最近 N 轮对话，丢弃更早的 → 简单但丢失长期信息
- **摘要压缩**：用 LLM 对历史对话生成摘要，用摘要替代原文 → 保留语义但损失细节
- **检索注入**：将历史对话存入向量数据库，每轮只注入最相关的片段 → 灵活但检索有延迟
- **分层管理**：最近 N 轮完整保留 + 更早的摘要 + 关键信息永久保留（用户偏好、重要决策）
- **灵汐印证**：灵汐的 memory/context_compressor.py 实现了上下文压缩，memory/history_buffer.py 管理对话历史缓冲，三层决策模型（筛选→注入→检索）控制注入量

### 维度五：工程实践与系统设计

#### Q13 ⭐⭐ 【流式输出实现】
**问题**：LLM 的流式响应是怎么实现的？SSE 和 WebSocket 各自的优缺点？

**参考答案要点**：
- **实现原理**：LLM 逐 Token 生成，每生成一个/一批 Token 就推送给客户端，而非等全部生成完
- **SSE（Server-Sent Events）**：
  - 优点：简单、HTTP 协议、自动重连、单向推送足够
  - 缺点：单向通信（服务端→客户端），有浏览器并发连接数限制
- **WebSocket**：
  - 优点：全双工、低延迟、无连接数限制
  - 缺点：实现复杂、需要额外的心跳机制
- **选择建议**：纯流式输出用 SSE，需要双向交互（如用户中断生成）用 WebSocket
- **灵汐印证**：灵汐的 ws_handler.py 用 WebSocket 实现双向通信，stream_handler.py 处理流式消息

#### Q14 ⭐⭐⭐ 【Agent 系统安全性】
**问题**：Agent 系统有哪些安全风险？你会如何设计安全防护体系？

**参考答案要点**：
- **风险清单**：
  - Prompt Injection：恶意用户通过输入注入指令，操控 Agent 执行危险操作
  - 工具滥用：Agent 被诱导调用危险工具（删文件、执行系统命令）
  - 数据泄露：Agent 在对话中泄露敏感信息
  - 资源耗尽：Agent 陷入无限循环或消耗大量 Token
- **防护体系**：
  - 输入过滤：检测和拦截 Prompt Injection
  - 工具权限分级：高危工具需人工审批
  - 执行隔离：沙箱环境，限制文件系统和网络访问
  - 循环保护：最大迭代次数限制 + 超时机制
  - 审计日志：记录所有工具调用和关键决策
- **灵汐印证**：灵汐的 isolation/（隔离执行环境）、security_check 插件（安全检查）、approval_guard（审批守卫）、core/audit.py（审计）构成了完整的安全防护体系

#### Q15 ⭐⭐⭐ 【灵汐 vs LangChain vs LangGraph 架构对比】
**问题**：请对比你自研的灵汐系统和 LangChain/LangGraph 的设计。为什么不用 LangChain？灵汐的设计有哪些优势？

**参考答案要点**：

| 对比维度 | 灵汐 Agent OS | LangChain | LangGraph |
|----------|---------------|-----------|-----------|
| **Agent 循环** | 自研管道引擎 PipelineEngine | AgentExecutor | StateGraph |
| **扩展机制** | IPlugin 标准接口 + 验证器 | Chain/Tool 继承 | Node 函数 |
| **状态管理** | State dict + StateKeys 常量 | Memory 对象 | TypedDict Graph State |
| **路由控制** | 5种路由信号 + 路由表仲裁 | Output Parser | 条件边 |
| **记忆系统** | TagWave + pgvector + 三层决策 | BufferMemory 系列 | Checkpoint |
| **工具系统** | 自研 + MCP 双向 | Tool 抽象 | Tool Node |
| **评估** | 统一评估引擎（9类指标） | 无内置 | 无内置 |
| **安全** | 隔离执行 + 审批 + 审计 | 无内置 | 无内置 |

- **不用 LangChain 的原因**：
  1. LangChain 抽象层太多，出问题难以定位
  2. AgentExecutor 是黑盒，定制困难
  3. 灵汐需要支持挂起/恢复（人工审批），LangChain 不原生支持
  4. 需要插件热替换和配置驱动，LangChain 不支持运行时热加载
- **灵汐的核心优势**：
  1. 引擎零业务逻辑——所有能力通过插件外置，扩展性极强
  2. 路由信号系统——比简单的 continue/stop 更丰富的控制流
  3. 内置安全体系——隔离、审批、审计一体化
  4. 统一评估——自动化质量保障
