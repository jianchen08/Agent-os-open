# 方案与执行计划模板

<!--
============================================================
【模板是什么】
本模板是任务执行前的"施工蓝图"与"任务排期表"的统一文档。
它定义了要做什么（需求）、为什么要做（调研）、怎么做（实施方案）、
做到什么程度算完成（验收标准），以及如何将方案按内容边界打包为
调度单元并排期执行（任务链与执行顺序）。

【模板的作用】
1. 统一结构 — 所有方案与执行计划遵循相同结构，降低阅读和评审成本
2. 需求可追溯 — 每个验收项关联到具体需求，确保不遗漏
3. 方案可评审 — 关键决策、结构划分有据可查，支持团队评审
4. 风险可预判 — 提前识别风险并制定应对策略
5. 变更可追踪 — 版本记录保留所有变更历史
6. 任务可调度 — 将方案中的任务按内容边界打包为调度单元，明确依赖关系和验收标准

【核心设计原则】
1. 包是调度单元 — 任务链定义包，包给 L2 或直接给 L3
2. 按内容边界打包，不按人工工序拆 — 每个包应该是自包含的业务目标
3. 执行者灵活选择 — 需要编排用 L2，不需要编排直接用 L3
4. 同类型包优先合并 — 多个同类型包可以塞给同一个 L2，让它自己内部分配
5. 缺失资源内嵌标注 — 直接写在对应任务里，不单独汇总
6. L3 拆分指引仅对直通 L3 的包 — 给 L2 的包由 L2 自己决定内部拆法

【两层分割逻辑】
├── 任务链（L1 制定）
│   ├── 包 → L2 编排者（L2 自己内部拆分，任务链不管）
│   └── 包 → L3 直通（任务链给出上下文环境拆分指引）
│
│   上下文环境拆分指引维度（仅适用于直通 L3 的包）：
│   - 知识域：完成任务需要理解的知识范围（模块、概念、领域）
│   - 操作域：任务操作的文件/资源范围（目录、文件、API）
│   - 依赖域：对其他任务产出的依赖（前置产出、共享状态）

【如何使用本模板】
1. 按照各章节的字段说明填写内容
2. [必填] 章节必须填写，[可选] 章节按需填写
3. [按需] 章节根据方案类型决定是否填写
4. 保存到对应任务目录下

【适用场景】
- 软件开发：功能开发、架构设计、系统集成、问题修复
- 内容创作：小说、剧本、文案策划
- 活动策划：会议、展览、庆典
- 科研项目：实验设计、论文撰写
- 其他领域：任何需要系统规划的任务
- 需要编排的中大型任务（小任务直接派给 L3，不走任务链）
- 多任务协作场景
- 跨模块/跨板块的复杂任务

【占位符说明】
- {xxx}：需要替换为具体内容的占位符
- [必填]：必须填写的章节/字段
- [可选]：按需填写的章节/字段
- [按需]：根据方案类型决定是否填写的章节/字段
============================================================
-->

## 五、执行评估 [必填]

<!--
> **章节说明**：在分解任务之前，必须先评估任务的内容量和边界，

> 3. 每个包分配一个 L2 编排者
>

<!--
> **字段填写说明**：
>
> | 字段 | 类型 | 必填 | 说明 |
> |------|------|------|------|
> | 内容量预估 | string | 是 | 列出任务的自然单元及其预估大小 |

> **内容量预估说明**：
> - 识别任务的"自然单元"（章节、模块、接口、主题、功能点……）
> - 估算每个单元的大小（代码行数/字数/文件数等粗略指标）
> - 内容量分档：小（< 100K tokens）、中（100K~200K）、大（> 200K）
>
> **上下文打包原则**：
> - 能合并就合并，减少任务间上下文传递
> - 太大就拆开，避免单个任务超出上下文
> - 按内容边界打包（章节、模块等），不按人工工序拆

>
> **L2 编排者的容量放大效应**：
> - L2 不亲自执行，而是分给 L3 执行，因此能承载更多内容
> - 产出物（最终结果）：L2 可承载约 2~3 倍单个上下文窗口的产出量
> - 含中间消耗（读取 L3 输出、编排决策、上下文传递）：可承载约 4~6 倍
> - 给 L2 的包可以比给 L3 的包大得多，不要按 L3 的限制来估算 L2 的包大小
-->
