# 执行计划模板

<!--
============================================================
【模板是什么】
执行计划是方案确认后的"任务排期表"，将方案中的任务按内容边界
打包为 L2 编排单元，明确依赖关系、验收标准和缺失资源。

【核心设计原则】
1. 以上下文容量为硬约束 — 任务分解的根本原因是 LLM 上下文窗口限制
2. 按内容边界打包，不按人工工序拆 — 每个任务应该是自包含的
3. 执行者灵活选择 — 需要编排用 L2，不需要编排直接用 L3
4. 同类型包优先合并 — 多个同类型包可以塞给同一个 L2，让它自己内部分配
5. 缺失资源内嵌标注 — 直接写在对应任务里，不单独汇总

【适用场景】
- 需要编排的中大型任务（小任务直接派给 L3，不走执行计划）
- 多任务协作场景
- 跨模块/跨板块的复杂任务

【与其他模板的关系】
- 上游：基于 solution_template.md（方案文档）创建
- 下游：主 Agent 按计划派发任务给 L2 编排者
============================================================
-->

## 执行评估 [必填]

<!--
> **章节说明**：在分解任务之前，必须先评估任务的内容量和边界，
> 据此决定如何打包和分配。这是执行计划的第一个关键决策。
>
> **核心逻辑**：
> 1. 内容量能塞进一个上下文 → 小任务（但走到这里说明需要编排）
> 2. 按内容边界打包，弹性合并小单元，大单元单独成包
> 3. 每个包分配一个 L2 编排者
>
> **注意**：真正的小任务（L3 直通能搞定）不会走到执行计划这一步，
> 上层会直接派给 L3 执行。
-->

- **内容量预估**: {content_estimation}
- **上下文打包方案**: {packing_plan}
- **判定依据**: {judgment_basis}

<!--
> **字段填写说明**：
>
> | 字段 | 类型 | 必填 | 说明 |
> |------|------|------|------|
> | 内容量预估 | string | 是 | 列出任务的自然单元及其预估大小 |
> | 上下文打包方案 | string | 是 | 按上下文容量将单元分组的方案 |
> | 判定依据 | string | 是 | 一句话说明为什么这样打包 |
>
> **内容量预估说明**：
> - 识别任务的"自然单元"（章节、模块、接口、主题、功能点……）
> - 估算每个单元的大小（代码行数/字数/文件数等粗略指标）
> - 内容量分档：小（< 100K tokens）、中（100K~200K）、大（> 200K）
>
> **上下文打包原则**：
> - 能合并就合并，减少任务间上下文传递
> - 太大就拆开，避免单个任务超出上下文
> - 按内容边界打包（章节、模块等），不按人工工序拆
> - 小单元可以多个合并，大单元可以单独一个包
>
> **L2 编排者的容量放大效应**：
> - L2 不亲自执行，而是分给 L3 执行，因此能承载更多内容
> - 产出物（最终结果）：L2 可承载约 2~3 倍单个上下文窗口的产出量
> - 含中间消耗（读取 L3 输出、编排决策、上下文传递）：可承载约 4~6 倍
> - 给 L2 的包可以比给 L3 的包大得多，不要按 L3 的限制来估算 L2 的包大小
-->

**填写示例**：

- **内容量预估**:
  - 用户模块：约 8 个接口，预估中等（~80K tokens）
  - 商品模块：约 12 个接口，预估较大（~150K tokens）
  - 订单模块：约 10 个接口，预估较大（~120K tokens）
- **上下文打包方案**:
  - 包1 = [用户模块] → 单独一个任务
  - 包2 = [商品模块] → 单独一个任务
  - 包3 = [订单模块] → 单独一个任务
- **判定依据**: 三个模块各自内容量大，且有清晰的模块边界，按模块各自独立打包

---

> **其他示例**：
>
> **中篇小说场景**（上下文够，不拆）：
> - **内容量预估**:
>   - 全书 10 章，共约 57000 字（约 80K tokens）
> - **上下文打包方案**:
>   - 包1 = [第1-10章] → 全书合并，共约 80K tokens，一个上下文能装下
> - **判定依据**: 全书约 80K tokens，在上下文范围内，合并为一个任务交给一个 L2 编排即可
>
> **网络小说场景**（上下文不够，按卷拆）：
> - **内容量预估**:
>   - 全书 300 章，约 200 万字（约 3000K tokens），远超上下文限制
>   - 第一卷（1-50章）：约 33 万字（~500K tokens）
>   - 第二卷（51-100章）：约 33 万字（~500K tokens）
>   - 第三卷（101-200章）：约 66 万字（~1000K tokens）
>   - 第四卷（201-300章）：约 66 万字（~1000K tokens）
> - **上下文打包方案**:
>   - L2 编排者含中间消耗可承载 4~6 倍上下文（约 400K~600K tokens）
>   - 包1 = [第一卷 1-50章] → ~500K tokens，一个 L2 能承载
>   - 包2 = [第二卷 51-100章] → ~500K tokens，一个 L2 能承载
>   - 包3 = [第三卷 101-200章] → ~1000K tokens，超出单 L2 承载，拆成两个包
>     - 包3a = [第101-150章] → ~500K tokens
>     - 包3b = [第151-200章] → ~500K tokens
>   - 包4 = [第四卷 201-300章] → ~1000K tokens，同理拆成两个包
>     - 包4a = [第201-250章] → ~500K tokens
>     - 包4b = [第251-300章] → ~500K tokens
> - **判定依据**: 按卷为单位打包，单卷超 500K tokens 的再按章拆分，每个包控制在 L2 承载范围内
>
> **科研项目场景**（多板块，按内容边界拆）：
> - **内容量预估**:
>   - 文献综述：需阅读 50+ 篇论文，产出约 3 万字综述（~200K tokens 含输入）
>   - 实验设计：方案文档 + 数据集说明，约 1 万字（~50K tokens）
>   - 数据分析：数据集 + 分析代码 + 结果报告，约 2 万字（~150K tokens 含数据）
>   - 论文撰写：正文 + 图表 + 参考文献，约 1.5 万字（~80K tokens）
> - **上下文打包方案**:
>   - 包1 = [文献综述] → 单独一个任务，含输入约 200K tokens
>   - 包2 = [实验设计] → 单独一个任务，约 50K tokens
>   - 包3 = [数据分析] → 单独一个任务，含数据约 150K tokens
>   - 包4 = [论文撰写] → 单独一个任务，约 80K tokens
> - **判定依据**: 文献综述含大量输入超出单上下文需单独处理，其余各板块有明确边界，按板块拆分
>
> **调研场景**（上下文够，不拆）：
> - **内容量预估**:
>   - 竞品分析：约 5000 字
>   - 用户画像：约 3000 字
>   - 市场趋势：约 4000 字
> - **上下文打包方案**:
>   - 包1 = [竞品分析 + 用户画像 + 市场趋势] → 合并，共 12000 字，一个任务搞定
> - **判定依据**: 总量不大，可合并为一个任务
