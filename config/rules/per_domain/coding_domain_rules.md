# 编程领域规则

---

## 一、核心原则

### 1.1 需求第一，一字不增

- 只实现需求文档明确描述的功能
- 区分"不言自明的系统需求"（操作连贯性、状态反馈、安全底线）与"有争议的体验假设"（用户没说的一律不做）
- 禁止任何"用户可能想…"的假设

### 1.2 最小输出

- 只输出完成任务必需的最少代码
- 禁止冗余：无多余 try-catch、空 else、假 fallback、console.log、TODO
- 一行能解决的不写两行

### 1.3 严格复用与边界尊重

- 写新代码前先查阅现有接口，优先复用
- 绝不访问模块私有成员，只使用公开接口
- 遇阻碍（如缺少参数）必须先沟通，禁止静默绕过或重写已有API

### 1.4 错误处理铁律

- 要么处理要么传播，禁止吞异常
- 禁止空 catch 块或仅日志记录的错误处理
- 错误是值，应可恢复，边界处翻译错误，日志与用户提示分离

### 1.5 Bug修复安全

- **止血不截肢**：修复Bug必须定位并修改精确错误，严禁退回旧方案或绕开
- **重构时须注入模块需求清单**，确保外部行为不变

## 二、编码规范

### 2.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 变量/函数 | camelCase（JS/TS）或 snake_case（Python） | `getUserInfo`, `get_user_info` |
| 类/接口 | PascalCase | `UserService`, `HttpClient` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 私有成员 | _leadingUnderscore | `_internalState` |
| 布尔变量 | is/has/can/should 前缀 | `isActive`, `hasPermission` |

### 2.2 代码风格

- **函数式优先**：优先纯函数，避免副作用
- **单文件 < 300 行**：超过则拆分模块
- **圈复杂度**：具体阈值见 code_writer_rules.md
- **函数行数 < 50 行**：过长则拆分
- **参数个数 ≤ 4**：超过则使用对象封装

### 2.3 TypeScript 规范

- 严格模式（strict: true）
- 禁用 any（除非有明确注释说明原因）
- 接口优于 type（除非需要联合类型/交叉类型）
- 启用 noImplicitAny、strictNullChecks

### 2.4 Python 规范

- 遵循 PEP 8
- 类型注解：具体规范见 python_type_hints.md 和 code_writer_rules.md
- docstring：公共函数/类必须有 docstring
- import 顺序：标准库 → 第三方 → 本地

### 2.5 Go 规范

- 命名：导出用 PascalCase，私有用 camelCase，包名简短全小写
- 错误处理：`if err != nil` 显式处理，不用 panic 处理常规错误
- 接口：小而专（1-3 个方法），由消费方定义而非实现方
- 格式化：强制 `gofmt` + `goimports`
- 测试：`_test.go` 与源文件同包，使用标准 `testing` 包

### 2.6 React / 前端规范

- 组件命名 PascalCase，文件名与组件名一致（`UserCard.tsx`）
- Hooks 命名强制 `use` 前缀（`useUserList`）
- 不可变状态：永远不直接 mutate state，用展开运算符/解构创建新对象
- 事件处理：`handleClick`（类组件）/ `onClick` 接收（函数组件）
- 测试：Jest + React Testing Library，测试用户行为而非实现细节

## 三、文件组织

### 3.1 目录结构约定

```
src/
├── modules/          # 业务模块（按功能域划分）
│   ├── auth/         # 认证模块
│   └── user/         # 用户模块
├── shared/           # 共享代码（跨模块复用）
│   ├── utils/        # 工具函数
│   └── types/        # 共享类型定义
├── infrastructure/   # 基础设施层
└── config/           # 配置文件
tests/
├── unit/             # 单元测试（镜像src结构）
├── integration/      # 集成测试
└── fixtures/         # 测试固件
```

### 3.2 模块边界

- 每个模块有清晰的公共接口（index.ts / __init__.py）
- 模块间通过公共接口通信，禁止跨模块访问内部文件
- 共享代码放 shared/，业务代码放 modules/
- 禁止循环依赖

## 四、测试要求

### 4.1 覆盖率标准

具体标准见 testing_rules.md

### 4.2 测试编写规范

- **AAA 模式**：Arrange（准备）→ Act（执行）→ Assert（断言）
- **一个测试只验证一件事**
- **测试名描述意图**：`should_reject_login_with_expired_token` 而非 `test_login_1`
- **Mock 最小化**：只 Mock 外部依赖（网络、数据库），不 Mock 被测代码内部

## 五、Git 工作流

### 5.1 Conventional Commits 1.0.0

格式：`<type>[scope]: description`

| type | 用途 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档变更 |
| style | 代码格式（不影响功能） |
| refactor | 重构（不新增功能、不修复Bug） |
| perf | 性能优化 |
| test | 测试相关 |
| build | 构建系统/依赖变更 |
| ci | CI配置变更 |
| chore | 杂项（不修改src或tests） |
| revert | 回退之前 的commit |

- 破坏性变更用 `!` 标记或 body 中 `BREAKING CHANGE:` 前缀
- scope 可选，表示影响范围（如 `auth`, `api`）
- description 简明扼要，小写，不加句号

### 5.2 分支策略

- `main`：生产分支，只接受合并，不直接提交
- `develop`：开发分支
- `feature/*`：功能分支
- `fix/*`：修复分支
- PR 必须通过所有检查才能合并

## 六、审查清单（七大维度）

### 6.1 设计层面

- 是否有重复代码（散点）？→ 提取公共逻辑
- 是否有边界泄漏？→ 模块间只通过公共接口通信
- 接口是否暴露了易变实现细节？→ 分离稳定与易变

### 6.2 功能正确性

- 边界条件是否处理（空值、零值、最大值、溢出）？
- 错误路径是否测试？
- 是否有死代码？

### 6.3 可读性

- 命名是否表达意图？
- 是否有过长的函数/过深的嵌套？
- 注释是否解释"为什么"而非"做什么"？

### 6.4 可测试性

- 依赖是否可注入？
- 是否有全局状态/副作用？
- 测试是否覆盖了关键路径？

### 6.5 性能

- 是否有 N+1 查询？
- 是否有不必要的大对象拷贝？
- 是否有潜在的内存泄漏？

### 6.6 安全

- 是否有注入风险（SQL/XSS/命令注入）？
- 敏感数据是否加密存储/传输？
- 权限检查是否到位？
- 是否硬编码密钥/Token/URL？（必须使用环境变量或配置文件）
- 是否使用 `eval()` / `exec()` / `Function()`？（禁止用于用户输入）
- 依赖是否有已知漏洞？（定期运行 `npm audit` / `pip-audit` / `snyk test`）
- 文件上传是否校验类型/大小/路径？（防止目录穿越）

### 6.7 工程实践

- 是否遵循项目的目录结构和命名约定？
- 是否更新了相关文档？
- 是否有硬编码的配置值（应提取到配置文件）？

## 七、AI 编程五段式工作流

所有 AI 编程任务遵循以下五段式流程：

```
1. 上下文加载 → 2. 计划确认 → 3. 代码生成 → 4. 验证修复 → 5. 提交归档
```

### 7.1 上下文加载

- 读取项目规则文件（.cursorrules / CLAUDE.md / 本文件）
- 读取相关代码文件，理解现有结构
- 确认技术栈、依赖版本、编码风格

### 7.2 计划确认

- 先给出实施计划（改哪些文件、怎么改），不直接改代码
- 等待用户/上级确认后再执行
- 复杂变更须列出风险评估

### 7.3 代码生成

- 按计划逐文件修改
- 每次改动保持最小化
- 遵循编码规范

### 7.4 验证修复

- 改完跑 lint + typecheck + test
- 如有失败，修复后重新验证
- 确保零警告（`--max-warnings 0`）

### 7.5 提交归档

- 使用 Conventional Commits 格式提交
- 更新相关文档
- 标注 breaking change（如有）

## 八、反模式清单（明确禁止）

| 反模式 | 说明 | 正确做法 |
|--------|------|----------|
| console.log 残留 | 生产代码中有调试日志 | 用正式日志框架 |
| any / @ts-ignore | 类型系统中断 | 正确标注类型或添加注释说明原因 |
| 直接 mutate state | 导致不可预测行为 | 使用不可变更新 |
| 硬编码密钥/URL | 安全风险 | 使用环境变量/配置文件 |
| 重复造轮子 | 已有库/函数可用却自己实现 | 先搜索现有实现 |
| 静默吞异常 | 隐藏问题 | 要么处理要么传播 |
| 过早抽象 | 只有一个使用场景就抽象 | 等到第三次重复再抽象 |
| 无测试提交 | 代码无测试覆盖 | 新增代码必须附带测试 |
| 破坏性静默更改 | 不兼容API变更未标注 | 使用 `!` 或 `BREAKING CHANGE` |
| 方案倒退 | Bug修复时退回旧方案 | 定位精确错误并修复 |

## 九、质量门禁

### 9.1 Pre-commit Hook

提交前自动检查：
- Lint（ESLint / Ruff / mypy）
- 格式化（Prettier / Black）
- 类型检查（TypeScript / mypy）
- 快速测试（smoke test）

### 9.2 CI/CD 流水线

```
Lint → Type Check → Unit Test → Integration Test → Build → Deploy
```

- 任何阶段失败阻塞合并

### 9.3 质量门禁量化指标

| 指标 | 阈值 | 说明 |
|------|------|------|
| 新增代码覆盖率 | ≥ 80% | 行覆盖 + 分支覆盖 |
| 新增代码重复率 | < 3% | 避免复制粘贴 |
| 新增 Bug 数 | 0 | SonarQube Bug 规则 |
| 新增漏洞数 | 0 | 安全漏洞 |
| 新增异味数 | < 5 | 代码异味（Code Smell） |
| 单元测试通过率 | 100% | 不允许失败用例 |
| Lint warning | 0 | `--max-warnings 0` |
| 圈复杂度 | < 10 | 过高则提取子函数 |
