# 编程场景核心上下文规则

---

## 概述

### 规则目的

本规则定义了灵汐系统编程场景下 Agent 获取编码上下文的标准化流程。通过明确信息获取顺序、任务类型上下文范围、文档层级规范和先读后写原则，确保 Agent 在编码时能够获取完整、准确的上下文信息，产出高质量代码。

### 适用范围

本规则适用于所有编程相关的 Agent 任务，包括但不限于：
- 新模块开发
- 现有模块修改
- Bug 修复
- 重构优化
- 测试编写

### 来源标识说明

| 标识 | 含义 | 说明 |
|------|------|------|
| [STD] | 标准规范 | 来自国际标准、行业标准（RFC、W3C等） |
| [BEST] | 最佳实践 | 社区公认的最佳实践和方法论 |
| [DOC] | 官方文档 | 来自官方文档的推荐做法 |
| [TOOL] | 工具文档 | 来自工具的官方文档 |
| [TEAM] | 团队约定 | 团队内部约定的规范 |
| [RESEARCH] | 调研结论 | 基于系统调研的结论 |
| [FRAMEWORK] | 框架规范 | 基于系统已有框架的扩展 |

## 信息获取顺序（5级）

### 规则概述

编码前必须按照以下 5 级顺序获取上下文信息。每级使用指定工具获取对应内容，原因在「为什么」中说明。

### 层级定义

| 优先级 | 层级 | 获取什么信息 | 用什么工具 | 为什么 |
|--------|------|-------------|-----------|--------|
| 1 | **项目级** | 系统架构、API设计、配置文件、项目结构 | `file_read` 读取 `docs/project/` 目录 | 全局性修改、跨模块开发必须先理解整体架构 |
| 2 | **模块级** | 模块需求、逻辑结构、接口定义、模块依赖 | `file_read` 读取 `{模块}/{模块}.md` | 模块内开发需理解模块边界和对外接口 |
| 3 | **代码级** | 具体组件源码、函数实现、类型定义 | `file_read` 或 `enhanced_search` | 单组件开发需理解现有实现细节 |
| 4 | **规范级** | 代码风格、类型注解、命名约定 | `file_read` 读取 `config/rules/` 目录 | 确保代码符合团队编码规范 |
| 5 | **依赖级** | 第三方库文档、API参考、工具说明 | `fetch` 获取官方文档或 `memory` 检索 | 解决技术问题、正确使用依赖库 |

### 工具使用说明

| 工具 | 适用层级 | 使用场景 |
|------|---------|---------|
| `file_read` | 项目级、模块级、规范级 | 读取 Markdown 文档和源码文件 |
| `enhanced_search` | 代码级 | 搜索函数、类、变量的定义位置 |
| `fetch` | 依赖级 | 获取外部库的官方文档 |
| `memory` | 依赖级 | 检索已存储的领域知识 |

### 层级递进规则

来源：[FRAMEWORK] 基于 `document_context_rules.md` 扩展

```
1. 项目级文档 → 2. 模块级文档 → 3. 代码级源码 → 4. 规范级规则 → 5. 依赖级文档
     ↓                ↓                ↓               ↓              ↓
   理解架构        理解模块边界      理解实现细节     遵循编码规范     正确使用依赖
```

**强制规则**：必须按顺序递进，禁止跳级获取上下文。确需跨级时，应先完成中间层级的信息获取。

## 上下文范围（5种任务类型）

### 规则概述

根据任务类型不同，需要读取的上下文范围有所不同。本节定义每种任务类型的必需上下文和可选上下文。

### 任务类型定义

#### 1. 新模块开发

| 上下文类型 | 必需读取 | 说明 | 来源 |
|------------|---------|------|------|
| 项目级 | ✅ | `docs/project/charter.md`（架构）、`docs/project/` 目录 | 理解整体架构 |
| 模块级 | ✅ | 新模块的 `{模块}.md`（需新建） | 定义模块需求和结构 |
| 组件级 | ✅ | 组件级文档模板 | 理解组件设计要求 |
| 规范级 | ✅ | `config/rules/` 下所有规则 | 确保符合编码规范 |
| 依赖级 | ⬜ 可选 | 技术栈官方文档 | 选型确认 |

#### 2. 现有模块修改

| 上下文类型 | 必需读取 | 说明 | 来源 |
|------------|---------|------|------|
| 项目级 | ⬜ 跨模块时 | 相关项目级文档 | 理解架构影响 |
| 模块级 | ✅ | 模块的 `{模块}.md` | 理解模块边界 |
| 组件级 | ✅ | 待修改组件的 `{组件}.md` | 理解组件设计 |
| 代码级 | ✅ | 待修改的源码文件 | 理解具体实现 |
| 规范级 | ✅ | 相关规范文件 | 确保符合规范 |

#### 3. Bug修复

| 上下文类型 | 必需读取 | 说明 | 来源 |
|------------|---------|------|------|
| 错误日志 | ✅ | 错误堆栈、错误信息 | 定位问题入口 |
| 代码级 | ✅ | 报错位置的源码 | 理解问题原因 |
| 测试用例 | ✅ | 相关的测试文件 | 理解预期行为 |
| 模块级 | ⬜ 可选 | 上下文复杂时 | 理解模块设计 |
| 规范级 | ⬜ 可选 | 规范不明确时 | 参考规范 |

#### 4. 重构优化

| 上下文类型 | 必需读取 | 说明 | 来源 |
|------------|---------|------|------|
| 模块级 | ✅ | 模块的 `{模块}.md` | 确认重构范围 |
| 组件级 | ✅ | 待重构组件的文档 | 理解组件职责 |
| 代码级 | ✅ | 现有源码 | 分析重构点 |
| 测试覆盖 | ✅ | 测试文件 | 确认测试覆盖 |
| 规范级 | ✅ | 相关规范 | 确保重构后符合规范 |

#### 5. 测试编写

| 上下文类型 | 必需读取 | 说明 | 来源 |
|------------|---------|------|------|
| 代码级 | ✅ | 被测代码源码 | 理解被测逻辑 |
| 接口定义 | ✅ | 函数/类签名、API接口 | 理解接口契约 |
| 测试规范 | ✅ | `config/rules/testing_rules.md` | 遵循测试规范 |
| 示例测试 | ⬜ 可选 | 项目已有测试文件 | 参考测试风格 |
| Mock策略 | ⬜ 可选 | `testing_rules.md` Mock章节 | 确定Mock方式 |

### 上下文选择规则

来源：[RESEARCH] 系统调研结论

```
任务类型 → 确定必需上下文 → 按优先级读取 → 补充可选上下文 → 开始编码
```

**强制规则**：
1. 必需上下文必须全部读取方可开始编码
2. 可选上下文根据任务复杂度酌情补充
3. Bug修复优先读取错误日志和报错代码

## 文档规范（7层）

### 规则概述

文档是上下文传递的核心载体。本规范定义了 7 层文档结构，确保文档内容完整、结构清晰、索引便捷。

### 层级定义

| 层级 | 类型 | 描述 | 应包含内容 | 来源 |
|------|------|------|-----------|------|
| **1** | 项目级·需求 | 项目整体需求文档 | 功能需求、非功能需求、约束条件、关键决策 | [DOC] |
| **2** | 项目级·逻辑 | 项目整体逻辑文档 | 业务流程、数据流图、状态机、外部接口 | [DOC] |
| **3** | 项目级·结构 | 项目结构文档 | 目录结构、模块关系、配置文件说明 | [DOC] |
| **4** | 模块级·需求 | 模块需求文档 | 模块功能、输入输出、外部依赖、验收标准 | [DOC] |
| **5** | 模块级·逻辑 | 模块逻辑文档 | 内部逻辑、数据结构、算法说明 | [DOC] |
| **6** | 模块级·结构 | 模块结构文档 | 文件清单、类/函数列表、接口定义 | [DOC] |
| **7** | 模块级·实现 | 模块实现指向 | 指向源码文件，具体实现在代码中 | [FRAMEWORK] |

### 文档放置规则

来源：[BEST] 文档跟随代码原则

```
项目根目录/
├── docs/
│   └── project/           # 项目级文档
│       ├── charter.md     # 项目宪章（需求）
│       ├── logic.md       # 项目逻辑
│       └── structure.md   # 项目结构
├── {模块名}/              # 模块目录
│   ├── {模块名}.md        # 模块级文档（需求+逻辑+结构）
│   ├── {组件名}/          # 组件目录
│   │   └── {组件名}.md    # 组件文档
│   └── {模块名}.py        # 源码实现
└── config/
    └── rules/             # 规范级文档
```

### 文档索引规则

来源：[FRAMEWORK] 基于 `document_context_rules.md`

每层文档必须包含「结构」章节作为索引入口：

```markdown
## 结构

- [项目级文档索引]
  - [需求文档]
  - [逻辑文档]
  - [结构文档]
- [模块级文档索引]
  - [模块A]
  - [模块B]
```

### 文档更新规则

来源：[TEAM] 团队约定

| 操作 | 必须同步更新的文档 |
|------|-------------------|
| 新增接口/配置 | 对应的模块级文档 + 项目级文档 |
| 新增文件 | 所在模块的「结构 > 文件清单」 |
| 新增组件 | 创建组件级文档（需求+逻辑+结构） |
| 修改逻辑 | 更新模块级·逻辑文档 |

### 文档编写禁止规则

来源：[STD] 文档与实现分离原则

**禁止事项**：
1. [STD] 禁止在文档中写具体实现代码
2. [STD] 禁止在文档中使用未定义的缩写或术语
3. [BEST] 禁止创建无索引入口的文档

## 先读后写规则（5条）

### 规则概述

编码前必须先读取相关上下文，遵循「先读后写」原则，确保编码决策有据可依。

### 规则列表

#### 规则 1：确定模块归属

来源：[FRAMEWORK] 系统框架规范

```
编码任务 → 确定模块归属 → 读取模块级文档 → 理解模块边界 → 再动手编码
```

**具体要求**：
1. 编码前必须明确目标模块
2. 读取模块级文档（`{模块}/{模块}.md`）
3. 确认模块边界和对外接口
4. 跨模块修改需同时读取相关模块文档

#### 规则 2：按索引定位

来源：[BEST] 最佳实践

```
查找内容 → 定位文档 → 读取「结构」章节 → 通过索引定位 → 不盲目搜索
```

**具体要求**：
1. 每层文档通过「结构」章节索引入口
2. 禁止盲目使用 `enhanced_search` 搜索全项目
3. 搜索前先确认目标文档的「结构」章节

#### 规则 3：新增文件更新清单

来源：[TEAM] 团队约定

```
新增文件 → 立即更新「结构 > 文件清单」→ 保持文档与代码同步
```

**具体要求**：
1. 新增任何文件必须更新所在模块的「文件清单」
2. 更新时机：编码完成后立即更新文档
3. 清单格式：`{文件名} - {文件用途} - {创建时间}`

#### 规则 4：新增组件创建文档

来源：[TEAM] 团队约定

```
新增组件 → 创建组件级文档 → 包含需求+逻辑+结构 → 再编码
```

**具体要求**：
1. 新增组件必须创建对应文档
2. 文档必须包含：需求说明、逻辑说明、结构说明
3. 文档模板参考 `docs/templates/component_template.md`

#### 规则 5：修改前确认测试覆盖

来源：[BEST] 测试驱动原则

```
修改代码 → 检查测试覆盖 → 无覆盖则先补充测试 → 有覆盖再修改
```

**具体要求**：
1. 修改现有代码前先确认是否有测试覆盖
2. 无测试覆盖的代码修改属于高风险操作
3. 优先补充测试，再进行代码修改
4. 重构必须先确认测试覆盖

## 前后端规则路由

### 路由机制

来源：[RESEARCH] 方案设计决策（S001）

通过 `coding_context_rules` 中的路由机制决定加载 `frontend_rules` 或 `backend_rules` 的判断逻辑：

```
code_writer_agent
  └── static_vars:
        coding_context_rules    ← 核心上下文规则（必加载）
        frontend_rules           ← 前端专用规则（按需加载）
        backend_rules           ← 后端专用规则（按需加载）
        testing_rules           ← 测试规则
```

### 路由决策逻辑

| 判断条件 | 加载规则 | 示例场景 |
|---------|---------|---------|
| `project.tech_stack` 包含前端技术 | 加载 `frontend_rules` | React/Vue/Angular 项目 |
| `project.tech_stack` 包含后端技术 | 加载 `backend_rules` | FastAPI/Django/Flask 项目 |
| `project.tech_stack` 同时包含前后端 | 加载两者 | 全栈项目 |
| 显式指定 `@frontend` | 加载 `frontend_rules` | 用户指定 |
| 显式指定 `@backend` | 加载 `backend_rules` | 用户指定 |

### 规则加载示例

```yaml
# code_writer_agent.yaml
static_vars:
  coding_context_rules: config/rules/coding_context_rules.md
  frontend_rules: config/rules/frontend_rules.md      # 条件加载
  backend_rules: config/rules/backend_rules.md        # 条件加载
  testing_rules: config/rules/testing_rules.md        # 条件加载
```

### 未匹配规则处理

来源：[RESEARCH] 方案设计结论

- 未匹配的规则默认不加载，避免干扰
- 规则路由基于项目技术栈配置自动判断
- 可通过 `@frontend` / `@backend` / `@testing` 显式指定

## 领域规则索引

### 规则文件关系

来源：[RESEARCH] 系统调研结论

```
coding_context_rules.md (核心上下文规则)
    │
    ├── frontend_rules.md (前端开发规范)
    │       └── 引用: testing_rules.md (前端E2E测试)
    │
    ├── backend_rules.md (后端开发规范)
    │
    └── testing_rules.md (测试规范)
            └── 引用: frontend_rules.md (前端E2E测试章节)
```

### 规则引用关系

| 规则文件 | 被引用 | 引用 |
|---------|-------|------|
| `coding_context_rules.md` | frontend/backend/testing | 引用所有领域规则 |
| `frontend_rules.md` | - | 引用 `testing_rules.md` (E2E测试) |
| `backend_rules.md` | - | 独立维护 |
| `testing_rules.md` | frontend_rules.md | 独立维护 |

### 加载优先级

| 优先级 | 规则文件 | 说明 |
|-------|---------|------|
| 1 | `coding_context_rules.md` | 必加载，定义上下文获取流程 |
| 2 | `frontend_rules.md` 或 `backend_rules.md` | 根据技术栈二选一 |
| 3 | `testing_rules.md` | 测试相关任务时加载 |
