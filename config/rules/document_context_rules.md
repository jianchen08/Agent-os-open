# 上下文读取与文档规范

> 工作时请遵循以下原则：先读文档理解上下文，再动手执行；创建文档按规范，保持文档与实际一致。

---

## 一、执行前：先读文档再动手

**信息获取顺序（5级）**：项目级 → 模块级 → 代码级 → 规范级 → 依赖级

| 优先级 | 层级 | 获取什么信息 | 用什么工具 | 为什么 |
|--------|------|-------------|-----------|--------|
| 1 | **项目级** | 系统架构、API设计、配置文件、项目结构 | `file_read` 读取 `.project/` 目录 | 全局性修改、跨模块开发必须先理解整体架构 |
| 2 | **模块级** | 模块需求、逻辑结构、接口定义、模块依赖 | `file_read` 读取 `{模块}/{模块}.md` | 模块内开发需理解模块边界和对外接口 |
| 3 | **代码级** | 具体组件源码、函数实现、类型定义 | `file_read` 或 `enhanced_search` | 单组件开发需理解现有实现细节 |
| 4 | **规范级** | 代码风格、类型注解、命名约定 | `file_read` 读取 `config/rules/` 目录 | 确保代码符合团队编码规范 |
| 5 | **依赖级** | 第三方库文档、API参考、工具说明 | `fetch` 获取官方文档或 `memory` 检索 | 解决技术问题、正确使用依赖库 |

**强制规则**：必须按顺序递进，禁止跳级获取上下文。确需跨级时，应先完成中间层级的信息获取。

**索引使用**：每层文档的"结构"章节是索引入口，通过索引定位，不要盲目搜索。

**上下文范围**：
- 单模块 → 该模块文档 + 项目级（如需依赖）
- 多模块 → 所有相关模块文档 + 项目级
- 全局架构 → 项目级 + 所有受影响模块

### 按任务类型的上下文范围

根据任务类型不同，需要读取的上下文范围有所不同：

#### 1. 新模块开发

| 上下文类型 | 必需读取 | 说明 |
|------------|---------|------|
| 项目级 | ✅ | `.project/charter.md`（架构）、`.project/` 目录 |
| 模块级 | ✅ | 新模块的 `{模块}.md`（需新建） |
| 组件级 | ✅ | 组件级文档模板 |
| 规范级 | ✅ | `config/rules/` 下所有规则 |
| 依赖级 | ⬜ 可选 | 技术栈官方文档 |

#### 2. 现有模块修改

| 上下文类型 | 必需读取 | 说明 |
|------------|---------|------|
| 项目级 | ⬜ 跨模块时 | 相关项目级文档 |
| 模块级 | ✅ | 模块的 `{模块}.md` |
| 组件级 | ✅ | 待修改组件的 `{组件}.md` |
| 代码级 | ✅ | 待修改的源码文件 |
| 规范级 | ✅ | 相关规范文件 |

#### 3. Bug修复

| 上下文类型 | 必需读取 | 说明 |
|------------|---------|------|
| 错误日志 | ✅ | 错误堆栈、错误信息 |
| 代码级 | ✅ | 报错位置的源码 |
| 测试用例 | ✅ | 相关的测试文件 |
| 模块级 | ⬜ 可选 | 上下文复杂时 |
| 规范级 | ⬜ 可选 | 规范不明确时 |

#### 4. 重构优化

| 上下文类型 | 必需读取 | 说明 |
|------------|---------|------|
| 模块级 | ✅ | 模块的 `{模块}.md` |
| 组件级 | ✅ | 待重构组件的文档 |
| 代码级 | ✅ | 现有源码 |
| 测试覆盖 | ✅ | 测试文件 |
| 规范级 | ✅ | 相关规范 |

#### 5. 测试编写

| 上下文类型 | 必需读取 | 说明 |
|------------|---------|------|
| 代码级 | ✅ | 被测代码源码 |
| 接口定义 | ✅ | 函数/类签名、API接口 |
| 测试规范 | ✅ | `config/rules/testing_rules.md` |
| 示例测试 | ⬜ 可选 | 项目已有测试文件 |
| Mock策略 | ⬜ 可选 | `testing_rules.md` Mock章节 |

**强制规则**：
1. 必需上下文必须全部读取方可开始编码
2. 可选上下文根据任务复杂度酌情补充
3. Bug修复优先读取错误日志和报错代码

### 先读后写规则（5条）

1. **确定模块归属**：编码任务 → 确定模块归属 → 读取模块级文档 → 理解模块边界 → 再动手编码；跨模块修改需同时读取相关模块文档
2. **按索引定位**：查找内容 → 定位文档 → 读取「结构」章节 → 通过索引定位，禁止盲目用 `enhanced_search` 搜索全项目
3. **新增文件更新清单**：新增任何文件必须更新所在模块的「结构 > 文件清单」（`{文件名} - {文件用途} - {创建时间}`），编码完成后立即更新
4. **新增组件创建文档**：新增组件必须创建对应文档（需求说明+逻辑说明+结构说明），参考 `docs/templates/component_template.md`
5. **修改前确认测试覆盖**：修改现有代码前先确认是否有测试覆盖；无覆盖的修改属于高风险，优先补测试再改；重构必须先确认测试覆盖

## 二、项目文档在哪里

项目文档统一存放在 `.project/` 目录，**全部平铺不分子文件夹**：

| 文件类型 | 命名 | 性质 |
|----------|------|------|
| 宪法文档 | `{type}_charter.md` | 冻结，项目最高准则 |
| 项目规则 | `{type}_rules.md` | 跟着项目走的特定规则 |
| 其他文档 | 自由命名 | 架构、大纲、API设计等 |

**关键区分**：
- `.project/` = 项目级文档，执行任务前检查是否有相关文档
- `docs/working/` = 中间过程文档，用于存放调研笔记、草稿等临时产出

## 三、创建/修改文档：按规范来

| 层级 | 位置 | 内容 |
|------|------|------|
| 项目级 | `.project/` | 架构、API、配置、宪法 |
| 模块级 | `{模块}/{模块}.md` | 需求、逻辑、结构 |
| 组件级 | `{模块}/{组件}/{组件}.md` | 需求、逻辑、结构 |

**四阶段**：需求 → 逻辑 → 结构 → 实现（指向下层）

**规则**：
1. 修改接口/配置时必须同步更新文档
2. 新增文件时添加"结构 > 文件清单"条目
3. 新增组件/模块时创建对应文档
4. 禁止在文档中写具体实现代码
5. 文档跟随代码（放在模块代码同层）
