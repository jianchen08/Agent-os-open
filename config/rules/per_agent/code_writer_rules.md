# Code Writer Agent 规则文件

## 第一部分：通用规则

---

### 1. Clean Code 原则

#### 有意义命名 [error]

变量、函数、类名必须表达意图，禁止使用无意义的名称。

**规则要求**：
- 变量名应描述其持有的数据含义
- 函数名应描述其执行的操作
- 类名应准确反映其职责
- 禁止单字母命名（循环变量 i/j/k 除外）
- 禁止名称缩写，除非是公认的行业缩写
- 禁止魔法数字，必须使用有名称的常量

#### 小函数 [error]

函数体应该简短，只做一件事。

**规则要求**：
- 函数体不超过 50 行
- 每个函数只执行一个明确的操作
- 如果函数名包含"并且/或者"，应拆分为多个函数
- 优先提取公共逻辑到独立函数

#### 单一职责 [error]

每个模块、类、函数只有一个变更原因。

**规则要求**：
- 模块只负责一块相关功能
- 类的职责边界清晰，不做超出范围的事
- 函数只完成单一任务，不承担多重责任
- 当需求变更时，大部分变更应只影响一个模块

#### DRY 原则 [warning]

Don't Repeat Yourself，不重复自己。

**规则要求**：
- 相同逻辑不出现两次以上
- 提取公共逻辑到工具函数或基类
- 配置数据集中管理
- 避免复制粘贴代码片段

#### KISS 原则 [warning]

Keep It Simple and Stupid，保持简单直接。

**规则要求**：
- 避免过度设计和不必要的复杂性
- 优先使用简单直接的解决方案
- 不要为了"扩展性"添加不必要的抽象层
- 代码应容易被理解和修改

#### 童子军规则 [optional]

离开代码时让它比发现时更好。

**规则要求**：
- 每次提交时修复一个小问题（命名、格式、注释）
- 不在新代码中引入代码异味
- 发现问题顺手修复，不留技术债务
- 保持代码渐进式改进

#### 寻找根本原因 [error]

不掩盖问题，不使用 work-around，找到根因再修复。

**规则要求**：
- 修复问题而非症状
- 禁止使用临时方案绕过后续彻底解决
- 当无法找到根因时，添加 TODO 注释说明
- 单元测试应覆盖边界条件和错误场景

### 2. 代码生成标准

#### 参数数量 [error]

函数参数应精简明确。

**规则要求**：
- 函数参数不超过 3 个
- 超过 3 个参数应封装为配置对象或结构体
- 相关参数应归类为对象传递
- 避免传递可选参数过多，考虑使用选项模式

#### 圈复杂度 [error]

函数逻辑应保持简单。

**规则要求**：
- 函数圈复杂度不超过 10
- 超过 10 则拆分为多个简单函数
- 减少嵌套层级，优先使用卫语句提前返回
- 条件判断过复杂时提取为独立函数

#### 组合优先继承 [warning]

优先使用组合模式而非继承。

**规则要求**：
- 优先通过组合实现代码复用
- 继承层级不超过两层
- 优先使用接口而非具体实现
- 优先使用委托而非继承

#### 类型注解 [error]

所有公共函数必须有类型注解。

**规则要求**：
- 参数必须有类型注解
- 返回值必须有类型注解
- 复杂数据结构使用泛型或自定义类型
- 避免使用 any 类型

#### 无副作用 [warning]

函数应避免隐式副作用。

**规则要求**：
- 函数应避免修改全局状态
- 避免修改传入参数
- 副作用函数必须通过命名明确表达
- 优先使用纯函数

#### 依赖注入 [warning]

通过参数注入依赖，不硬编码外部依赖。

**规则要求**：
- 外部依赖通过参数传入
- 使用依赖注入容器管理依赖关系
- 便于单元测试时替换实现
- 降低模块间的耦合度

### 3. 输出质量标准

#### 可读性 [error]

代码应自文档化，复杂逻辑必须有注释说明。

**规则要求**：
- 代码结构清晰，格式一致
- 复杂业务逻辑添加解释性注释
- 公共 API 添加文档注释
- 避免过度简化的缩写导致难以理解

#### 可维护性 [warning]

代码结构清晰，模块边界明确，低耦合。

**规则要求**：
- 模块边界清晰，职责单一
- 模块间通过定义良好的接口通信
- 相关代码按功能组织在一起
- 代码修改应局限在最小范围

#### 可测试性 [warning]

代码设计应便于测试，依赖可 Mock。

**规则要求**：
- 核心逻辑提取为独立函数
- 外部依赖通过接口抽象
- 避免硬编码难以测试的逻辑
- 提供测试所需的钩子方法

#### 外科手术式修改 [error]

只触碰必须触碰的代码，禁止"顺便"改进相邻代码。

**规则要求**：
- 每一行修改必须能追溯到用户请求
- 禁止顺手改注释、格式化、重命名未提及的变量
- 禁止重构未被要求重构的代码
- 相邻代码视为禁区，除非显式要求
- 发现需改进的代码时，记录在注释中而非直接修改

#### 透明完成 [error]

不确定时必须明确说出来，禁止静默完成。

**规则要求**：
- 任务未完全完成时，必须报告完成百分比和不确定的部分
- 禁止将模糊结果标记为"完成"或"成功"
- 验证未通过时，明确说明哪些验证通过、哪些未通过
- 宁可说"完成了 80%，剩下 20% 不确定"，也不要假装全部完成

### 4. Fallback 与兼容性

#### 降级按需设计 [error]

降级/Fallback 不是默认要求，不要滥用。只有涉及**外部依赖**（第三方 API、外部服务、不可控环境）的功能才需要设计降级方案。内部模块之间不存在降级问题——你控制双方，直接改就行。

**规则要求**：
- 仅对外部依赖设计降级方案，内部调用不需要降级
- 不涉及外部依赖的功能，正常写错误处理即可，不需要 fallback
- 降级方案的设计必须在有明确的外部故障场景时才有价值

#### 兼容仅限外部依赖 [error]

兼容性只考虑一种情况：**需要兼容外部依赖**（第三方接口、外部协议、客户端版本不可控等）。内部代码双方都在你的控制范围内，不存在兼容问题——直接统一升级。

**规则要求**：
- 内部模块间接口变更：直接改，不保留旧接口
- 内部数据结构变更：直接迁移，不保留旧格式解析
- 外部依赖接口变更：按兼容性铁律处理
- 外部客户端不可控时：才需要考虑向后兼容

#### 功能完整性优先 [error]

当确实需要兼容/降级时，前提是用户预期的功能和使用体验不能有任何缺失。兼容是"用不同的方式达到相同的结果"，而不是"得到一个残缺的结果"。

**规则要求**：
- 任何降级/兼容方案不得导致核心功能缺失或不可用
- 降级后用户应获得等价的功能完成度，仅允许性能轻微下降
- 禁止以兼容为名行阉割之实（如"老环境不支持某特性就不做该功能"）
- 降级方案必须保证用户数据不丢失、操作可继续

**优先级链条**（从高到低）：
1. 功能完整性（不可妥协）
2. 数据正确性（不可妥协）
3. 用户体验完整性（不可妥协）
4. 兼容性（仅限外部依赖，尽量满足）
5. 性能（可接受轻微下降）
6. 代码优雅度（最先牺牲）

#### 渐进降级 [warning]

对外部依赖确实需要降级时，每一步降级都必须是可预期的、有意识的设计。方案 A（最优）失败 → 方案 B（次优）→ 方案 C（兜底）。

**规则要求**：
- 降级路径必须明确，不能依赖运气或偶然行为
- Fallback 本身也要有 Fallback，但不能无限递归
- 到最终兜底时，宁可抛出明确错误，也不能假装一切正常

#### 降级策略分层 [warning]

不同类型的功能应采用不同的降级策略，禁止一刀切。

**规则要求**：
- UI 展示类（头像加载失败、样式缺失）→ 静默降级（显示默认值）
- 数据一致性类（支付、状态变更）→ 明确报错，禁止静默降级
- 非关键路径（埋点上报、统计日志）→ 静默丢弃 + 本地缓存重试
- 核心业务流程（任务提交、消息发送）→ 阻塞并明确告知用户

#### 兼容性铁律 [error]

仅当需要兼容外部依赖时适用。

**规则要求**：
- 新增是安全的，删除/修改是危险的。字段只能增不能删，废弃字段保留默认值
- 永远不要假设外部调用方的存在：新代码不能假设老调用方会传新字段（必须有默认值），老代码不能假设新调用方会传老字段（必须容忍缺失）
- 有计划地淘汰而非突然断裂：Deprecate（标记废弃）→ Warn（警告期）→ Remove（移除），每个阶段至少经历一个版本
- 不信任外部输入：所有外部输入都做校验，兼容性不等于放任
