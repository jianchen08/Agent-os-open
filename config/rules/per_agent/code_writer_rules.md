# Code Writer Agent 规则文件

【本文档是什么】
Code Writer Agent 的 per-agent 规则文件，定义代码编写的质量标准和最佳实践。

【本文档的作用】
1. 规范代码编写过程中的命名、结构和设计原则
2. 定义前端和后端代码的特殊要求
3. 确保产出代码的可读性、可维护性和可测试性
4. 预防常见代码质量问题和安全漏洞

1. 代码编写前：阅读通用规则部分，理解核心原则
2. 前端开发：额外遵循前端版规则
3. 后端开发：额外遵循后端版规则
4. 代码评审：对照规则检查代码是否符合标准

- 后端代码编写：Java/Python/Go 等后端服务
- API 设计：RESTful API 接口开发
- 全栈开发：同时涉及前后端的项目

- 上游：基于通用编程规范

## 第一部分：通用规则

<!--
通用规则适用于所有代码编写场景，不分前端或后端。
-->

### 1. Clean Code 原则

#### 有意义命名 [error]

变量、函数、类名必须表达意图，禁止使用无意义的名称。

**规则要求**：
- 变量名应描述其持有的数据含义
- 函数名应描述其执行的操作
- 类名应准确反映其职责
- 禁止单字母命名（循环变量 i/j/k 除外）
- 禁止名称缩写，除非是公认的行业缩写
- 禁止魔法数字，必须使用有名称的常量

#### 小函数 [error]

函数体应该简短，只做一件事。

**规则要求**：
- 函数体不超过 50 行
- 每个函数只执行一个明确的操作
- 如果函数名包含"并且/或者"，应拆分为多个函数
- 优先提取公共逻辑到独立函数

#### 单一职责 [error]

每个模块、类、函数只有一个变更原因。

**规则要求**：
- 模块只负责一块相关功能
- 类的职责边界清晰，不做超出范围的事
- 函数只完成单一任务，不承担多重责任
- 当需求变更时，大部分变更应只影响一个模块

#### DRY 原则 [warning]

Don't Repeat Yourself，不重复自己。

**规则要求**：
- 相同逻辑不出现两次以上
- 提取公共逻辑到工具函数或基类
- 配置数据集中管理
- 避免复制粘贴代码片段

#### KISS 原则 [warning]

Keep It Simple and Stupid，保持简单直接。

**规则要求**：
- 避免过度设计和不必要的复杂性
- 优先使用简单直接的解决方案
- 不要为了"扩展性"添加不必要的抽象层
- 代码应容易被理解和修改

#### 童子军规则 [optional]

离开代码时让它比发现时更好。

**规则要求**：
- 每次提交时修复一个小问题（命名、格式、注释）
- 不在新代码中引入代码异味
- 发现问题顺手修复，不留技术债务
- 保持代码渐进式改进

#### 寻找根本原因 [error]

不掩盖问题，不使用 work-around，找到根因再修复。

**规则要求**：
- 修复问题而非症状
- 禁止使用临时方案绕过后续彻底解决
- 当无法找到根因时，添加 TODO 注释说明
- 单元测试应覆盖边界条件和错误场景

### 2. 代码生成标准

#### 参数数量 [error]

函数参数应精简明确。

**规则要求**：
- 函数参数不超过 3 个
- 超过 3 个参数应封装为配置对象或结构体
- 相关参数应归类为对象传递
- 避免传递可选参数过多，考虑使用选项模式

#### 圈复杂度 [error]

函数逻辑应保持简单。

**规则要求**：
- 函数圈复杂度不超过 10
- 超过 10 则拆分为多个简单函数
- 减少嵌套层级，优先使用卫语句提前返回
- 条件判断过复杂时提取为独立函数

#### 组合优先继承 [warning]

优先使用组合模式而非继承。

**规则要求**：
- 优先通过组合实现代码复用
- 继承层级不超过两层
- 优先使用接口而非具体实现
- 优先使用委托而非继承

#### 类型注解 [error]

所有公共函数必须有类型注解。

**规则要求**：
- 参数必须有类型注解
- 返回值必须有类型注解
- 复杂数据结构使用泛型或自定义类型
- 避免使用 any 类型

#### 无副作用 [warning]

函数应避免隐式副作用。

**规则要求**：
- 函数应避免修改全局状态
- 避免修改传入参数
- 副作用函数必须通过命名明确表达
- 优先使用纯函数

#### 依赖注入 [warning]

通过参数注入依赖，不硬编码外部依赖。

**规则要求**：
- 外部依赖通过参数传入
- 使用依赖注入容器管理依赖关系
- 便于单元测试时替换实现
- 降低模块间的耦合度

### 3. 输出质量标准

#### 可读性 [error]

代码应自文档化，复杂逻辑必须有注释说明。

**规则要求**：
- 代码结构清晰，格式一致
- 复杂业务逻辑添加解释性注释
- 公共 API 添加文档注释
- 避免过度简化的缩写导致难以理解

#### 可维护性 [warning]

代码结构清晰，模块边界明确，低耦合。

**规则要求**：
- 模块边界清晰，职责单一
- 模块间通过定义良好的接口通信
- 相关代码按功能组织在一起
- 代码修改应局限在最小范围

#### 可测试性 [warning]

代码设计应便于测试，依赖可 Mock。

**规则要求**：
- 核心逻辑提取为独立函数
- 外部依赖通过接口抽象
- 避免硬编码难以测试的逻辑
- 提供测试所需的钩子方法

### 4. UI/UX 质量

#### 语义化标记 [error]

使用语义化 HTML 标签，不滥用 div/span。

**规则要求**：
- 使用 `<button>` 而不是 `<div onclick>`
- 使用 `<nav>` 定义导航区域
- 使用 `<main>` 定义主要内容
- 使用 `<article>`、`<section>`、`<aside>` 划分内容结构
- 表单使用 `<form>`、`<label>`、`<input>` 语义标签

#### 可访问性 [error]

所有交互元素可通过键盘操作，图片有 alt 文本，表单有 label。

**规则要求**：
- 所有可点击元素可通过 Tab 键聚焦
- 使用 `aria-label` 为图标按钮提供说明
- 图片必须提供 alt 文本描述
- 表单字段必须有关联的 label
- 颜色对比度满足 WCAG 标准

#### 视觉一致性 [warning]

遵循设计系统，统一间距/颜色/字体。

**规则要求**：
- 使用设计系统定义的色板、字体、间距
- 相同类型元素使用一致的样式
- 遵循既定的布局规范和间距规则
- 组件样式与设计稿保持一致

---

### 5. 性能优化

#### 渲染性能 [error]

避免不必要的重渲染，列表使用虚拟化。

**规则要求**：
- 组件状态变更应精准触发更新
- 列表数据量大时使用虚拟滚动
- 避免在渲染函数中创建新函数或对象
- 使用 React.memo/Vue.memo 等避免不必要重渲染

#### 懒加载 [warning]

非首屏资源使用懒加载。

**规则要求**：
- 首屏不需要的资源使用动态导入
- 图片使用懒加载（Intersection Observer）
- 路由组件按需加载
- 第三方库按需引入

#### 防抖节流 [warning]

高频事件使用防抖或节流。

**规则要求**：
- 搜索输入使用防抖（debounce）
- 滚动事件使用节流（throttle）
- 窗口 resize 事件使用防抖
- 表单验证使用防抖减少验证频率

---

### 6. 状态管理

#### 状态分层 [error]

区分组件状态、页面状态、全局状态，使用合适的管理方式。

**规则要求**：
- 组件内部状态使用 useState/ref
- 跨组件共享状态使用 Context/Store
- 全局状态使用状态管理库
- 不要将所有状态提升到全局

#### 不可变性 [error]

状态更新必须保持不可变，禁止直接修改。

**规则要求**：
- 使用展开运算符或浅拷贝创建新对象
- 数组操作使用 push/splice 返回新数组
- 嵌套对象深拷贝时使用 appropriate 方法
- 禁止使用 mutable 数组/对象方法直接修改

#### 数据流 [warning]

单向数据流，状态提升到共同父组件。

**规则要求**：
- 状态只能通过 props 传递给子组件
- 子组件通过回调函数修改父组件状态
- 避免双向绑定
- 跨层级通信使用 Context 或事件总线

---

### 7. 组件化

#### 组件拆分 [warning]

超过 150 行的组件考虑拆分。

**规则要求**：
- 单一组件代码行数不超过 150 行
- 超过 150 行拆分为子组件
- 每个组件只负责渲染和交互
- 业务逻辑提取到 hooks 或工具函数

#### Props 接口设计 [error]

Props 必须有类型定义，可选属性有默认值。

**规则要求**：
- 使用 TypeScript interface 定义 Props 类型
- 可选属性明确标记
- 可选属性提供合理默认值
- 复杂 Props 类型拆分独立定义

---

### 8. XSS 防护

#### 输入输出转义 [error]

所有用户输入必须转义后再渲染。

**规则要求**：
- 用户输入内容必须经过转义处理
- 使用框架提供的默认转义机制
- 禁止使用 dangerouslySetInnerHTML 除非确有必要
- 富文本使用专业过滤库处理

#### CSP 策略 [warning]

配置内容安全策略，禁止内联脚本。

**规则要求**：
- 配置严格的 CSP 策略
- 禁止内联脚本执行
- 限制资源加载来源
- 配置 report-uri 收集违规报告

### 9. API 设计

#### RESTful 规范 [error]

使用名词复数资源路径，正确使用 HTTP 方法。

**规则要求**：
- URL 使用名词复数形式（如 /users 而非 /getUser）
- 正确使用 HTTP 方法语义
- GET 查询、POST 创建、PUT 完整更新、PATCH 部分更新、DELETE 删除
- 符合 RESTful 设计规范

#### 资源命名 [error]

URL 使用小写 kebab-case，层级表示资源关系。

**规则要求**：
- URL 全部使用小写字母
- 多词使用 kebab-case 分隔（如 user-profiles）
- 层级反映资源归属关系（如 /users/{id}/orders）
- 查询参数使用 camelCase

#### 版本控制 [warning]

API 必须有版本控制，推荐 URL 路径方式。

**规则要求**：
- API 版本通过 URL 路径或 Header 表示
- 版本号使用语义化版本（如 v1、v2）
- 新版本保持兼容性或明确说明 breaking changes
- 旧版本提供迁移指南

---

### 10. 数据一致性

#### 事务处理 [error]

涉及多表操作必须使用事务。

**规则要求**：
- 多表关联操作必须在事务内执行
- 事务边界清晰，提交回滚明确
- 长事务拆分为可管理的多个小事务
- 事务超时设置合理

#### 并发控制 [warning]

共享资源使用乐观锁或悲观锁。

**规则要求**：
- 高并发场景使用版本号控制
- 关键数据使用分布式锁
- 选择合适的锁粒度
- 避免死锁，确保锁的获取顺序一致

---

### 11. 安全防护

#### 输入验证 [error]

所有外部输入必须验证（类型、范围、格式）。

**规则要求**：
- 参数类型和范围必须验证
- 字符串格式使用正则验证
- 数字参数检查边界值
- 集合类型检查长度和元素
- 禁止信任任何外部数据

#### 权限控制 [error]

每个 API 端点必须有权限校验。

**规则要求**：
- API 调用前验证用户身份
- 基于角色的访问控制（RBAC）
- 资源归属验证防止越权访问
- 敏感操作需要二次确认

#### 敏感数据 [error]

密码必须加密存储，日志中禁止记录敏感信息。

**规则要求**：
- 密码使用强哈希算法存储
- 敏感数据加密传输（HTTPS）
- 日志中脱敏处理敏感信息
- 密钥通过环境变量或密钥管理服务管理

---

### 12. 可扩展性

#### 松耦合 [warning]

模块间通过接口通信，不直接依赖实现。

**规则要求**：
- 使用接口或抽象类定义模块边界
- 依赖注入实现解耦
- 事件驱动替代直接调用
- 插件机制支持扩展

#### 模块化 [warning]

功能按领域划分模块，模块可独立部署。

**规则要求**：
- 按业务领域划分模块
- 模块间通过定义良好的 API 通信
- 模块可独立部署和扩展
- 避免模块间循环依赖

---

### 13. 错误处理

#### 具体异常 [error]

捕获具体异常类型，禁止裸 catch。

**规则要求**：
- 捕获特定异常类型
- 为每种异常提供对应处理
- 禁止使用 catch(Exception) 而不处理
- 未知异常应重新抛出或记录

#### 异常链 [warning]

使用异常链保留原始异常信息。

**规则要求**：
- 捕获异常时保留原始堆栈
- 使用异常的 cause 传递上下文
- 自定义异常包含原始异常引用
- 日志记录完整的异常链路

#### 日志规范 [error]

错误必须记录完整上下文，使用结构化日志。

**规则要求**：
- 记录异常堆栈信息
- 包含请求 ID 便于追踪
- 使用结构化日志格式（JSON）
- 敏感信息脱敏后记录
