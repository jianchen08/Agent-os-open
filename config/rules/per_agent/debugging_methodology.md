# Bug 调试方法论


## 总原则

**先确认"谁在执行"，再优化"怎么执行"。**

绝大多数深层 bug 不在报错代码本身，而在对象生命周期或编排层。直接在报错位置反复修改是最大的时间浪费。

---

## 规则 1：自顶向下，不要自底向上

**错误做法**：看到 `AuthenticationError` → 立刻去检查 API key 格式、provider 前缀、litellm 参数。
**正确做法**：先确认"这个错误是从哪个对象/实例抛出的"，再往下追。

操作步骤：
1. 在报错的最顶层入口加标记（print/logger），确认是哪个对象实例在执行
2. 在所有可能的分支/实现都加标记，而不是只在你"认为"正确的那个加
3. 标记内容至少包含：`type(self).__name__` 和关键参数

```python
# 正确示例：在所有适配器的 _do_completion 都加标记
class LiteLLMAdapter:
    async def _do_completion(self, **kwargs):
        print(f"[DIAG] adapter={type(self).__name__} model={kwargs.get('model')}")
        ...

class AdaptiveRouterAdapter:
    async def _do_completion(self, **kwargs):
        print(f"[DIAG] adapter={type(self).__name__} model={kwargs.get('model')}")
        ...
```

**为什么**：自底向上调试容易困在底层细节，忽略高层的对象替换、工厂重建、注册表 fork 等编排问题。

---

## 规则 2：隔离测试通过 ≠ 系统正确

**教训**：连续写了 6 级隔离测试，全部通过。但实际系统仍然失败。

原因：隔离测试只验证"这段代码在给定输入下能正常工作"。但如果实际运行时这段代码根本没被调用（被另一个实例/实现替代了），测试通过反而是误导。

**规则**：
- 隔离测试只用于验证"这个函数/类的逻辑是对的"
- 隔离测试通过后，如果 bug 仍在，**立刻停止在隔离层继续修改**，转向系统集成层
- 隔离测试的通过不能作为"bug 已修复"的判断依据

**判断阈值**：如果隔离测试通过但完整系统仍失败，**最多再做 1 轮隔离测试确认**，然后必须切换到全链路追踪模式。

---

## 规则 3：追踪对象生命周期，而不是代码路径

本次 bug 的本质：

```
build_plugin_registry → LLMCore(adapter=AdaptiveRouterAdapter)  ✓
    ↓ registry.fork()
PipelineEngine.__init__ → LLMCore(config=...) → LiteLLMAdapter  ✗  ← adapter 丢失！
    ↓ _apply_agent_model_override
engine.run → 把 LiteLLMAdapter 当作 existing_adapter 传递      ✗
```

**bug 不在 LLM 调用层，而在插件注册表的 fork 机制。** 从始至终 LLM 相关代码都是对的。

**规则**：对于"功能 A 在测试中正常但在系统中失败"的 bug：
1. 在对象的**构造函数**加调用栈追踪，确认对象被创建了几次、由谁创建
2. 检查所有可能的工厂/fork/clone/rebuild 路径
3. 确认运行时实际使用的实例和你修改的是同一个

```python
# 在构造函数追踪对象创建
class LLMCore:
    def __init__(self, **kwargs):
        import traceback
        traceback.print_stack(limit=4)  # 只打印最近 4 层
        print(f"[DIAG] LLMCore created with adapter={type(kwargs.get('adapter')).__name__}")
```

## 规则 4：诊断要加在分叉点，不是执行点

**错误做法**：在 `_direct_call` 内部加了 20 行日志，详细记录每个参数。
**正确做法**：在 `_do_completion`（多态分叉点）和 `__init__`（创建点）各加 1 行标记。

分叉点是指：多个实现可能被执行的地方（多态/策略模式/插件注册表）。
执行点是指：具体实现内部。

**原因**：如果分叉点选错了实现，执行点内的所有日志都是在错误的代码上打的，完全没有参考价值。

---

## 规则 5：警惕 confirmation bias — 主动证伪，不要只验证

研究表明：

> 调试时，开发者倾向寻找支持自己假设的证据，而非尝试推翻它。

**本次表现**：
- 假设"bug 在 _direct_call 的参数合并" → 反复修改参数合并逻辑
- 每次修改后跑隔离测试，通过 → 觉得"快修好了" → 继续在这个方向深挖
- 从未质疑过"也许 _direct_call 根本没被调用"

**反制措施**：
- 每当修改后 bug 仍在，问自己："如果我的假设是错的，最可能的替代解释是什么？"
- 设立"放弃阈值"：同一方向尝试 3 次无效后，**强制切换假设**
- 用 print 在错误对象上打标记，而不是在"应该是正确"的对象上打标记

---

## 规则 6：插件/工厂系统的常见陷阱清单

当 bug 表现为"功能在简单场景正常但在完整流程失败"时，按此清单检查：

| 检查项 | 常见问题 |
|--------|---------|
| **fork/clone** | 是否只复制了 config 而丢失了 adapter/router 等运行时依赖？ |
| **工厂重建** | `type(obj)(config=...)` 是否漏传了构造函数参数？ |
| **单例 vs 多实例** | 以为是同一个对象，实际被重建了？ |
| **依赖注入** | 依赖是通过构造函数注入还是运行时获取？注入的是引用还是值？ |
| **缓存/全局状态** | `__pycache__`、模块级单例是否过期？ |
| **注册表同步** | 替换插件后，core_plugins 和 plugins 两个映射是否都更新了？ |

## 规则 7：5 Whys 根因分析


**原则**：连续问 5 次"为什么"，从表层症状追到系统根因。

**示例**：
1. 为什么报 `AuthenticationError`？→ API key 验证失败
2. 为什么 API key 验证失败？→ LiteLLMAdapter 使用了默认 key
3. 为什么使用了 LiteLLMAdapter？→ registry.fork() 重建时没传 adapter 参数
4. 为什么没传 adapter 参数？→ fork 只复制了 config，不知道有 adapter 属性
5. 为什么只复制 config？→ fork 方法设计时没考虑运行时注入的依赖

**根因**：fork 机制不支持运行时依赖的传递 → 修复 fork，而非修复 API key。

**使用时机**：
- 每次修复后 bug 仍在，对当前失败做一轮 5 Whys
- 当你发现自己在同一方向尝试第 2 次时，强制做一轮 5 Whys
- 5 Whys 的答案必须是**事实**（日志/堆栈/数据），不是猜测

## 规则 8：先收集数据，再分析


**原则**：在形成任何假设之前，先收集足够的事实数据。

**数据收集清单**：

| 数据类型 | 收集方式 | 目的 |
|---------|---------|------|
| 完整错误堆栈 | 捕获 traceback | 定位出错位置 |
| 对象类型和ID | `print(type(x).__name__, id(x))` | 确认是哪个实例 |
| 输入参数快照 | 打印关键参数值 | 排除参数错误 |
| 执行路径标记 | 在分叉点加 print | 确认走了哪条路径 |
| 对象创建栈 | `traceback.print_stack(limit=4)` | 追踪对象生命周期 |

**规则**：
- 收集数据阶段**不修改任何代码**（只加 print/diagnostic）
- 至少收集 2 轮数据后再形成假设
- 假设必须基于数据，不是直觉

---

## 规则 9：证据驱动的假设管理


**假设管理规则**：
- 同时维护的假设**不超过 3 个**
- 每个假设必须有**正面证据**和**反面证据**
- 排除假设比确认假设更有价值 — 被排除的假设不用再试

**假设模板**：

```
假设 H1：<描述>
  正面证据：<支持此假设的事实>
  反面证据：<与此假设矛盾的事实>
  验证方式：<如何证明/证伪>
  状态：待验证 / 已排除 / 已确认
```

**最大假设数规则**：如果 3 个假设都被排除了，不要生成第 4 个假设 — **回到数据收集阶段**，你大概率遗漏了关键信息。

---

## 规则 10：架构级熔断器


**规则**：连续 3 次修复尝试失败后，**停止修复**，进入架构重新评估。

**触发条件**（满足任一即触发）：
- 同一代码位置修改 3 次仍未通过
- 同一假设方向尝试 3 次无效
- 总修复轮次超过 6 次仍未解决

**熔断后的动作**：
1. 停止所有代码修改
2. 画出当前架构图（模块关系、数据流、对象生命周期）
3. 在架构图上标记"bug 发生位置"和"修复尝试位置"
4. 如果两者不在同一层 → 问题在架构层，不是代码层
5. 重新评估：是否需要修改的是框架/基础设施层？

**架构级问题的特征**：
- bug 在简单场景不出现，只在完整流程出现
- 隔离测试通过但集成测试失败
- 同一段代码在不同上下文中行为不同
- 对象/模块之间的交互关系与文档/假设不一致

## 规则 11：回归测试的正确写法


**原则**：回归测试必须验证**根本原因**被修复，而不仅仅是**症状**消失。

**错误示例**（只验证症状）：
```python
def test_no_auth_error():
    result = llm.call("hello")
    assert result is not None  # 通过了，但可能只是换了另一种方式失败
```

**正确示例**（验证根因）：
```python
def test_fork_preserves_adapter():
    """验证 fork 后 adapter 不丢失 — 这才是根因"""
    original = LLMCore(adapter=AdaptiveRouterAdapter(...))
    registry = PluginRegistry(plugins={"llm": original})
    forked = registry.fork()
    assert isinstance(forked._plugins["llm"]._adapter, AdaptiveRouterAdapter)
```

**回归测试清单**：
- 测试验证的是**根因条件**，不是**症状消失**
- 测试有明确的**断言消息**，说明断言的是什么
- 如果根因是对象生命周期问题，测试必须验证**对象身份**（type/id），不仅仅是值

---

## 规则 12：鱼骨图分析法


当 bug 原因不明时，按以下分类逐项排查：

```
                    Bug 症状
                       |
        ┌──────┬───────┼───────┬──────┐
        |      |       |       |      |
     代码层   数据层   环境层   编排层   配置层
```

| 分类 | 检查内容 |
|------|---------|
| **代码层** | 逻辑错误、边界条件、类型不匹配、异常未捕获 |
| **数据层** | 数据格式变化、缺失字段、编码问题、时序竞争 |
| **环境层** | 依赖版本、环境变量、文件权限、网络连通性 |
| **编排层** | 对象生命周期、插件注册、依赖注入、初始化顺序 |
| **配置层** | 配置文件格式、路径解析、默认值覆盖、合并策略 |

**使用时机**：当 5 Whys 分析到第 3 层仍找不到明确根因时，用鱼骨图分类排查。
