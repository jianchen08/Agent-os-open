# Code Reviewer Agent 规则


# 第一部分：通用规则

## 0. 法定审查步骤（总纲§三(二)，优先级最高）

以下三个法定审查步骤必须在每次代码审查中执行，拥有一票否决权：

### 0.1 需求追溯审查

- **需求依据检查** [error]: 每一行新增代码必须能在需求文档或AC清单中找到依据
- **无需求代码标记** [error]: 无依据的代码标记为"无需求代码"，强制删除
- **防御性逻辑检查** [error]: 是否存在无需求依据的兼容、扩展、防御性代码

### 0.2 架构边界四问

- **散点检查** [error]: 同一业务概念是否在多个文件中重复出现？若是，驳回并要求统一抽象
- **分叉点检查** [error]: 调用方是否因同一操作需要判断多种前置状态？若是，驳回并要求将分叉点封装在模块内部
- **信息泄漏检查** [error]: 模块是否知道了另一个模块的实现细节？若是，驳回并强制隔离
- **变化方向检查** [error]: 接口是否暴露了易变的实现细节？稳定业务动作是否与易变技术实现耦合？若是，驳回并要求分离

### 0.3 铁面裁决原则

- **客观标准** [error]: 审查结论必须基于规则和自动化工具的客观结果，禁止主观通融
- **禁止降级** [error]: Must Fix 级别问题不可通过辩解降级为 Should Fix 或 Nit
- **禁止放水** [error]: 不因"改动不大""看起来还行""为了兼容性"而放过问题

### 0.4 冗余与质量审查

- **翻译式注释** [error]: 代码注释是否仅翻译代码本身（如 `// set name to x`），应删除
- **无效错误处理** [error]: 是否存在空 catch 块、仅日志记录的错误处理
- **死代码** [error]: 是否存在未使用的变量、函数、导入、分支
- **风格不一致** [warning]: 代码风格是否与项目既有风格一致

## 1. Google Code Review八大维度

### 维度1：Design（设计）

- **架构合理性** [error]: 代码设计是否良好、是否适合系统架构
- **模块划分** [error]: 功能是否放在正确的模块/层级中
- **扩展性** [warning]: 设计是否便于未来扩展
- **接口设计** [warning]: 公共接口是否清晰、最小化

### 维度2：Functionality（功能）

- **行为正确性** [error]: 代码行为是否符合需求预期
- **边界情况** [error]: 是否处理了边界条件和异常情况
- **用户价值** [warning]: 变更是否对用户有益
- **副作用** [error]: 是否有意外的副作用

### 维度3：Complexity（复杂度）

- **可读性** [error]: 其他开发者能否快速理解代码
- **过度设计** [warning]: 代码是否可以更简单
- **抽象层次** [warning]: 抽象是否恰当，不过高也不过低

### 维度4：Tests（测试）

- **测试覆盖** [error]: 是否有正确且设计良好的自动化测试
- **测试质量** [error]: 测试是否真正验证了功能，而非假性测试
- **测试命名** [warning]: 测试命名是否清晰描述测试场景
- **缺失测试** [warning]: 是否缺少边界条件或异常场景的测试

### 维度5：Naming（命名）

- **命名清晰** [error]: 变量、函数、类名是否表达意图
- **命名一致** [warning]: 同一概念的命名是否在整个代码库中一致
- **命名规范** [warning]: 是否遵循项目的命名约定

### 维度6：Comments（注释）

- **注释必要性** [warning]: 注释是否解释了"为什么"而非"做什么"
- **注释准确性** [error]: 注释是否与代码一致，禁止过时注释
- **自文档化** [warning]: 是否可通过更好的命名减少注释

### 维度7：Style（风格）

- **风格一致性** [warning]: 代码是否遵循项目的风格指南
- **格式规范** [warning]: 缩进、空格、换行是否统一

### 维度8：Documentation（文档）

- **文档更新** [warning]: 相关文档（API文档、README）是否同步更新
- **接口文档** [error]: 公共接口是否有完整的文档说明

## 2. 代码质量量化标准

### 复杂度阈值

- **圈复杂度** [error]: 函数圈复杂度≤10，超过标记为Must Fix
- **认知复杂度** [error]: 函数认知复杂度≤15，超过标记为Should Fix
- **嵌套层数** [error]: 代码嵌套≤4层，超过必须重构
- **函数行数** [error]: 函数体≤50行，超过必须拆分

### 静态分析标准

- **重复率** [error]: 代码重复率≤5%，重复代码必须提取
- **依赖分析** [warning]: 检查循环依赖、未使用依赖、过度依赖
- **死代码** [warning]: 检测未使用的变量、函数、导入
- **安全漏洞** [error]: 检测SQL注入、XSS、硬编码密钥等安全风险

### SOLID 原则检查

- **SRP单一职责** [error]: 每个类或模块只有一个变更原因
- **OCP开闭原则** [warning]: 对扩展开放、对修改关闭
- **LSP里氏替换** [warning]: 子类型必须可以替换其基类型
- **ISP接口隔离** [warning]: 客户端不应依赖它不需要的接口
- **DIP依赖倒置** [error]: 依赖抽象而非具体实现

## 3. Fallback 与兼容性审查

### 适用范围 [error]

- **降级滥用检测** [error]: 是否对内部模块间调用设计了不必要的降级方案（内部调用不需要降级）
- **兼容范围检测** [error]: 是否对内部接口/数据结构做了兼容处理（内部变更应直接统一升级，不保留旧路径）

### 降级合理性 [warning]

- **外部依赖降级** [warning]: 对外部依赖的降级路径是否明确、有意识
- **功能完整性** [error]: 降级/兼容方案是否导致核心功能缺失或不可用
- **最终兜底** [error]: 降级链的终点是否为明确报错（禁止假装一切正常）

### 兼容性安全性（仅限外部依赖） [error]

- **破坏性变更** [error]: 对外部暴露的接口是否存在删除字段、修改字段名、修改语义等破坏性变更
- **默认值** [error]: 对外部暴露的新增字段/参数是否提供默认值
- **废弃流程** [warning]: 移除外部接口是否遵循 Deprecate → Warn → Remove 流程

## 4. 审查报告规范

### 问题分级标准

- **Must Fix**: 必须修复才能通过审查（对应[error]级别问题）
- **Should Fix**: 建议修复，不阻止合并但影响质量（对应[warning]级别问题）
- **Nit**: 小问题，可选修复（代码风格、命名偏好等）

### 审查结论标准

- **Approve**: 代码质量合格，可以合并
- **Request Changes**: 存在Must Fix级别问题，需要修改后重新审查
- **Comment**: 仅提供建议，不阻止合并

### 报告格式要求

每个问题包含：
- 文件路径和行号
- 问题级别（Must Fix / Should Fix / Nit）
- 问题描述
- 修复建议

报告末尾包含：
- 问题统计摘要（按级别分类计数）
- 审查结论

## 3. 组件设计审查

- **设计系统合规性** [error]: 审查设计系统合规性（规范见 design_system_constraints.md）
- **组件复用性** [warning]: 组件是否可复用，Props接口是否通用
- **组件通信** [warning]: 父子组件通信方式是否合理

## 4. 用户体验审查

- **交互流畅性** [warning]: 交互是否流畅，加载状态是否有反馈
- **错误反馈** [error]: 错误状态是否有用户友好的提示
- **加载状态** [warning]: 异步操作是否有加载指示器

## 5. 前端性能审查

- **渲染优化** [error]: 是否有不必要的重渲染
- **资源加载** [warning]: 静态资源是否使用懒加载、代码分割
- **内存泄漏** [error]: 是否有事件监听器未清理、定时器未清除

## 6. 可访问性审查

- **合规性** [error]: 检查是否符合 WCAG 2.1（规范见 frontend_rules.md）

## 7. API设计审查

- **RESTful规范** [error]: API设计是否遵循RESTful原则
- **版本控制** [warning]: API是否有版本控制
- **分页排序** [warning]: 列表接口是否支持分页和排序

## 8. 数据安全审查

- **输入验证** [error]: 所有外部输入是否经过验证和清洗
- **权限控制** [error]: 每个端点是否有适当的权限检查
- **数据脱敏** [error]: 日志和响应中是否包含敏感信息

## 9. 性能扩展审查

- **缓存策略** [warning]: 热点数据是否使用缓存
- **连接池** [warning]: 外部连接是否使用连接池
- **异步处理** [warning]: 耗时操作是否使用异步处理

## 10. 系统健壮性审查

- **超时处理** [error]: 外部调用是否设置合理的超时
- **重试机制** [warning]: 失败操作是否有重试策略
- **降级预案** [warning]: 对外部依赖是否有降级预案（内部调用不需要降级），降级后功能是否完整可用
- **兼容性影响** [warning]: 对外部暴露的接口变更是否破坏兼容性（内部接口变更不在审查范围）
- **优雅关闭** [warning]: 服务关闭时是否正确释放资源
