## 容器任务空间管理规则

### 空间类型与隔离机制

系统支持三种任务空间模式，理解它们的区别对正确管理任务至关重要：

| 模式 | 触发条件 | 空间行为 | 合并方式 |
|------|----------|----------|----------|
| 容器空间 | `task_scope="container"` | 创建独立容器目录，子任务各自创建 worktree 隔离副本 | 子任务 worktree 合并回容器空间 |
| 普通任务空间 | 默认（非容器非 host） | workspace 指向目标项目目录，系统创建 worktree 副本 | 完成后自动合并 |
| host 模式 | `isolation_level="host"` | 直接在原目录操作，不创建副本 | 无需合并（操作即时生效） |

### 核心规则

1. **容器空间是完全独立的**
   - 容器任务创建时会基于 workspace 参数创建独立的容器空间
   - 容器空间的生命周期是独立的，不依赖主空间
   - **容器完成后容器空间就是最终产物，不需要合并回原始 workspace**

2. **子任务的 worktree 隔离与合并**
   - 容器内的每个子任务在容器空间内各自创建 worktree（git 工作树副本）
   - worktree 是子任务的隔离副本，**不是主空间的直接映射**——子任务在 worktree 中的修改不会影响主空间
   - **子任务的 worktree 合并回容器空间**（而非主空间），由系统自动处理
   - 如果 worktree 合并回容器空间时出现冲突，需要手动介入处理

3. **子任务的 workspace 继承**
   - 容器任务的子任务必须通过 `parent_task_id` 关联到容器
   - 子任务的 workspace **自动继承容器空间**，无需手动指定
   - 不要为容器子任务单独设置 workspace，让系统自动处理继承

4. **同一项目归同一容器**
   - **同一项目的相关任务应放在同一个容器下管理**
   - 不要在容器空间之外用 host 模式修改同一项目的文件——应该把相关任务都放在同一个容器下管理
   - 禁止为同一项目创建多个容器，避免在多个空间产生重复版本和冲突
   - 如果已存在该项目的容器任务，新需求应作为子任务加入现有容器

5. **不使用 host 模式**
   - 你派发的所有任务统一走 container（worktree 副本），不开 host
   - 资源管理任务同样走 container
